# brigd

Локальный таск-трекер для **Codex CLI и Claude Code**. Создавайте задачи, задавайте интервалы, отвечайте на вопросы агента в карточке и сохраняйте историю каждого запуска.

**Bun · Svelte 5 · SQLite.** Один сервис со встроенной очередью SQLite, без прямых вызовов API моделей. Браузер открывает интерфейс на вашем компьютере. Расписание работает, только пока компьютер включён и сервис brigd запущен.

## Быстрый старт

Для Linux-контейнера начните с [Docker Compose: установка, тома и вход в CLI](docs/container.md). В образе есть оба CLI, а данные и сессии сохраняются в отдельных томах.

Для запуска без контейнера нужны [Bun](https://bun.sh/docs/installation) **1.3+** (проверено на 1.4.2) и Git. Для реальных задач установите хотя бы один CLI: [Codex](https://learn.chatgpt.com/docs/codex/cli) или [Claude Code](https://code.claude.com/docs/en/overview). Войдите в нужный CLI самостоятельно в терминале и убедитесь, что обычный запуск работает. brigd не просит API-ключи и не выполняет вход за вас.

```sh
git clone https://github.com/olntn/brigd.git brigd
cd brigd
bun install --frozen-lockfile
bun run doctor
bun run build
bun run start
```

Откройте **http://127.0.0.1:4310**. Терминал нужно оставить открытым. `Ctrl-C` корректно останавливает сервис и активные CLI-процессы.

Порт на одном компьютере занимает только один процесс: если `4310` уже используется, brigd не запустится и сообщит об этом. Второй экземпляр запускайте с другим портом, например `PORT=4320 bun run start`; разрешённые Host и Origin по умолчанию следуют за `PORT`, адрес будет `http://127.0.0.1:4320`. Изнутри контейнера занятость портов хоста не видна, поэтому для контейнера свободный порт выбирается на хосте при публикации (см. [контейнер](docs/container.md)).

`doctor` проверяет наличие CLI и поддержку нужных флагов через `--help`. Он не отправляет платные запросы и не проверяет вход/подписку. CLI должен быть доступен в `PATH` того терминала, из которого запускается brigd.

### Обновления при запуске

При `bun run start` brigd проверяет [стабильные GitHub Releases](https://github.com/olntn/brigd/releases). Если доступна более новая версия, он автоматически получает её исходники, устанавливает зависимости, собирает приложение и запускает обновлённую версию. Перезапускать уже работающий сервис ради обновления он не будет: сначала остановите его через `Ctrl-C`. Один каталог установки допускает один такой запуск одновременно; второй экземпляр с той же базой также не запускается.

Задачи, история, вложения и настройки остаются в прежней SQLite; рабочие папки и CLI-сессии сохраняют прежние пути. Значения из локального `.env` и окружения применяются как обычно. Скачанные версии хранятся в `.brigd-updates/` рядом с установкой; исходники в исходной папке и родительский Git-репозиторий не меняются. Механизм работает и в клоне репозитория, и в скопированной папке проекта. Версия выбранного приложения выводится при запуске.

Перед первым запуском новой версии создаётся согласованная резервная копия SQLite в `.brigd-updates/backup/`. Если миграция или запуск завершаются ошибкой до готовности сервера, база восстанавливается и запускается предыдущая версия. Автоматического отката после начала работы сервиса нет. Каталог с резервной копией хранится локально и не заменяет отдельную копию данных, CLI-сессий и проектов.

Без сети, при ошибке загрузки или при отсутствии стабильных релизов запускается последняя установленная версия. Управление запуском:

```sh
BRIGD_AUTO_UPDATE=0 bun run start  # последняя установленная версия без проверки GitHub
bun run start:local               # исходная версия из текущей папки без автообновления
```

Для установки, которая ещё не содержит этот механизм, один раз обновите исходники и зависимости обычным способом. После этого достаточно `bun run start`; вручную скачивать каждый следующий релиз не требуется. Docker и `bun run dev` используют прежний запуск; обновление контейнера описано в [инструкции Docker Compose](docs/container.md#данные-остановка-и-обновления).

### Выпуск версии

Автообновление получает опубликованные стабильные релизы; коммит в `main` сам по себе обновление не выпускает. Для релиза увеличьте `version` в `package.json`, сохраните `brigdUpdaterProtocol: 1` и отправьте тег `vX.Y.Z`, точно совпадающий с версией пакета. Workflow `.github/workflows/release.yml` проверит тег, совместимость протокола, типы, тесты и сборку, затем опубликует GitHub Release с автоматически составленным описанием. Теги с суффиксами предварительных версий не публикуются этим workflow. Команда публикации — [`gh release create <tag> --generate-notes --verify-tag`](https://cli.github.com/manual/gh_release_create).

### Сначала попробовать без запросов к моделям

```sh
bun run build
bun run demo
```

Откройте тот же адрес. В интерфейсе показана метка **Демо**. Создайте задачу с любой инструкцией и существующей абсолютной рабочей папкой:

- Обычный текст: тестовый агент завершает запуск
- Добавьте `[ask]`: агент задаёт уточняющий вопрос; ответ продолжает ту же тестовую сессию
- Добавьте `[blocked]`: демонстрация блокировки разрешений
- Добавьте `[fail]`: демонстрация ошибки
- Добавьте `[limit]`: демонстрация исчерпания лимитов CLI; `[limit:codex]` или `[limit:claude]` — только для указанного провайдера, чтобы увидеть, как задачу подхватывает работник замены из **Настройки → Общие** или из профиля работника

Это симуляция. Реальные CLI не запускаются, файлы рабочего проекта не меняются, запросов к модели нет. Демо использует отдельную базу `data/demo.sqlite`; обычный запуск — `data/trackt.sqlite`.

### Первая настоящая задача

1. Запустите `bun run start`, выберите **Новая задача**.
2. Укажите понятную инструкцию, нужный CLI и абсолютный путь к проекту. Для Codex используйте доверенный Git-репозиторий; brigd не отключает проверку репозитория.
3. Для первого теста выберите **Вручную**, сохраните и нажмите **Запустить**. Начните с безвредной задачи: «Кратко опиши структуру проекта, ничего не меняй».
4. Если агент запросит уточнение, ответьте в карточке. Кнопка продолжения передаст ответ в сохранённый ID сессии.
5. Для регулярной работы включите интервал и время первого запуска. Расписание работает локально, даже когда вкладка закрыта, пока запущен сервис.

Поле **Приоритет** в форме задачи принимает четыре значения: **Критический**, **Высокий**, **Обычный** (по умолчанию) и **Низкий**. Автопилот первой берёт задачу с более высоким приоритетом, а при равном приоритете — по порядку очереди (см. раздел «Автопилот»). Приоритет, отличный от обычного, показывается бейджем на карточке, в списке и в очереди автопилота; в заголовке открытой задачи он виден всегда. Задачи, созданные до появления поля, получают приоритет **Обычный**.

В форме задачи после выбора работника (у сложной задачи — после списка этапов) находится чекбокс **ultracode**. Пока галочка не тронута, он повторяет профиль назначенного работника; у сложной задачи — профили работников этапов, а при разных настройках этапов показывает неопределённое состояние. Без работника галочка по умолчанию снята, а режим определяют настройки установленного CLI; чтобы явно выключить его, поставьте и снимите галочку. Поставьте или снимите её, чтобы зафиксировать режим для новых запусков этой задачи независимо от профиля; у сложной задачи выбор действует на всех этапах. Выбор другого работника или работника этапа возвращает чекбокс к значению из его профиля; ссылка **Вернуть как в профиле работника** под чекбоксом делает то же для уже заданного выбора. На карточке на доске и в заголовке открытой задачи бейдж **ultracode** относится к тому же запуску, что и значок работника рядом: к текущему запуску, к последнему запуску сложной задачи или продолжения, а у простой задачи без активного запуска — к её следующему запуску. Требования к CLI описаны в разделе **Работники**.

В **Настройки → Общие** можно сохранить **Рабочую папку по умолчанию** — существующую папку с абсолютным путём. Она подставляется в новые задачи, где её можно изменить. Настройка сохраняется после перезапуска сервиса; рабочие папки уже созданных задач не меняются.

Там же задаётся **Тип запуска по умолчанию**: **Автопилот**, **Вручную** или **По расписанию**. Выбранный вариант подставляется в поле **Когда запускать** у новых задач, где его можно изменить. Для расписания изначально задан интервал 60 минут. Выбор сохраняется после перезапуска сервиса и не меняет тип запуска существующих задач; до настройки используется **Вручную**.

**Работник по умолчанию** подставляется в поле **Работник** у новых простых задач, чтобы не выбирать его каждый раз; в форме его можно заменить или убрать. Выбирать можно только активного работника. Если он позже попал в архив, настройка сохраняется, но в новые задачи не подставляется, пока профиль не восстановят или не выберут другого. Существующие задачи и этапы сложных задач не меняются. API: `GET/PATCH /api/settings/general` с полем `defaultWorkerId` (ID работника или `null`); MCP `get_general_settings` и `update_general_settings` принимают то же поле. `create_task` эту настройку не применяет: передайте `workerId` явно.

Блок **Замена при исчерпании лимитов** в том же разделе позволяет выбрать для Codex и для Claude Code работника, который подхватит задачу, когда CLI сообщит об исчерпании лимитов использования (usage limit, rate limit, quota, «try again at…»). Обычно это работник другого провайдера, например Codex Sol 6.1 ↔ Claude Code Opus 5.5: лимиты аккаунта общие для всех профилей одного CLI, поэтому замена тем же провайдером упрётся в тот же лимит. Замена срабатывает только для хода, который открывает новую сессию: первый запуск задачи, первый запуск этапа сложной задачи и повтор этапа. Работник замены получает то же задание, рабочую папку (включая уже созданный worktree), вложения и общие инструкции, но в новой сессии своего CLI со своими моделью, усилиями и личными инструкциями; в карточке появляется системный комментарий, в логах — запись с текстом ошибки CLI, а неудачный ход сохраняется в истории попыток этапа. Назначение задачи не меняется: следующий запуск снова начнёт исходный работник. Продолжение сохранённой сессии (ответ на вопрос или дополнительный запрос) не передаётся: другой CLI не может открыть чужую сессию, поэтому такой запуск завершается ошибкой с пояснением; Интегратор также не заменяется. На один ход выполняется одна замена: если работник замены тоже упёрся в лимит, запуск остаётся с ошибкой. Без настроенной замены ошибка запуска подсказывает, где её выбрать. В профиле отдельного работника можно задать **свою** замену — она имеет приоритет над общей настройкой. API: `GET/PATCH /api/settings/general` с полем `fallbackWorkers` вида `{"codex": "<id работника>", "claude": null}`; можно передать только один из ключей; замена должна быть активным работником, иначе `404` или `409`. Инструменты MCP `get_general_settings` и `update_general_settings` принимают то же поле.

В **Настройки → Язык** выбирается язык интерфейса: **Русский** (по умолчанию) или **English**. Переключение применяется сразу, без перезагрузки; выбор сохраняется в этом браузере, как и цветовая схема, и синхронизируется между открытыми вкладками. На английский переводятся надписи интерфейса, сообщения об ошибках API, записи логов и системные комментарии brigd. Названия и описания задач, комментарии, ответы агентов, страницы документации и другие введённые данные остаются на языке, на котором написаны. API, MCP и подсказки агентам продолжают работать на русском.

В **Настройки → Параллельность** задаётся, сколько задач выполняется одновременно: **Задач одновременно в одном репозитории** (по умолчанию 1, каждая задача — в своём Git worktree) и **Всего процессов** — агенты всех репозиториев вместе с проверками слияния (по умолчанию 4). Значения 1–32 применяются к следующим запускам без перезапуска сервиса; работающие задачи при уменьшении лимита не останавливаются. Параллельные задачи не мешают друг другу при переносе: результаты одного репозитория проверяются и сливаются строго по одному, каждый следующий — вместе с уже перенесёнными, а пока Интегратор разрешает конфликт, другие слияния этого репозитория ждут его. Подробности — в [инструкции очереди и слияний](docs/execution.md#параллельная-работа).

В **Настройки → Хранилище** видно, сколько места занимают рабочие папки запусков (Git worktree и кандидаты слияния): сколько можно освободить и сколько ещё нужно, с разбивкой по причинам и подсказкой, что сделать с каждой группой. После успешного переноса результата в целевую ветку ненужная папка запуска удаляется сама, затем удаляется и ветка `brigd/run-<ID>`, если она не изменилась после переноса и больше нигде не используется. Папки активных, прерванных, конфликтных, завершившихся ошибкой или блокировкой и ещё не перенесённых запусков, а также папки с репозиториями подмодулей сохраняются. Кнопка **Очистить** после подтверждения удаляет папки отменённых запусков и уже перенесённых результатов, устаревшие кандидаты слияния и папки запусков без записи в базе; по отдельной галочке — ещё и кандидаты неудачных проверок. Ветки уже перенесённых результатов удаляются по тем же правилам; ветки с неперенесённой работой остаются. Файлы, ссылки и папки, которые создал не brigd, только показываются и не удаляются. Продолжение сессии после удаления создаёт папку заново, при необходимости восстанавливая ветку из последнего перенесённого коммита. Подробности — в [инструкции очереди и слияний](docs/execution.md).

В **Настройки → Бэкапы** можно создать согласованную копию работающей базы, скачать её, загрузить сохранённый SQLite-файл до 256 МБ, переименовать, выбрать бэкап для восстановления или удалить ненужный. Кнопка **Переименовать** доступна у всех копий, включая выбранную и созданные перед обновлением. Новое имя сохраняется после перезапуска, восстановления и автообновления и используется при скачивании файла. В списке показаны дата, размер и источник, включая копии **Перед обновлением** из `.brigd-updates/backup/` исходной установки. Выбранный бэкап защищён от удаления и в интерфейсе, и в API; выбор сохраняется после перезапуска и восстановления базы.

У выбранного бэкапа есть чекбокс **Автообновление бэкапа**. При включении его файл сразу заменяется согласованной копией текущей базы, затем обновляется при изменениях в течение 5 секунд, пока сервис работает, в том числе при закрытом браузере. Перед обычным завершением сервиса сохраняются последние изменения. В списке отображается время обновления. Настройка сохраняется после перезапуска; отключение фиксирует последнюю копию, а выбор другого бэкапа выключает автообновление. Имя и ID файла сохраняются, остальные бэкапы не меняются.

Выбор бэкапа требует подтверждения и заменяет задачи, историю, настройки, профили и вложения данными из него. Перед восстановлением активные работники останавливаются и автоматически создаётся бэкап **Перед восстановлением** с текущими данными. Повреждённые или несовместимые файлы отклоняются; при ошибке открытия восстановленной базы возвращаются прежние данные. После успеха страница перезагружается. Рабочие папки проектов и CLI-сессии хранятся отдельно от SQLite и в такой бэкап не входят. Ручные и загруженные копии находятся в `backups/` рядом с базой, в отдельной подпапке для каждой базы.

Реальные запуски используют ваш CLI, его текущий аккаунт и лимиты/тариф. **Сохранить заметку** добавляет комментарий без запуска агента. Для ответа на текущий вопрос используйте **Продолжить работу**; для нового запроса после завершения или блокировки — **Отправить агенту** в обсуждении задачи.

Карточка открывается по центру: слева находятся задание, настройки, файлы и этапы, справа — **Комментарии**, **Логи**, **Изменения** и **Запуски**. Комментарии содержат ответы и вопросы агента, результаты и сообщения пользователя. В логах отдельно сохраняются действия работника: вызовы инструментов, операции с файлами, запуск и завершение команд. Раскройте запись, чтобы увидеть доступные сведения об операции, файлах, состоянии и коде завершения. У неудачных действий есть блок **Ошибка** с текстом причины и кнопкой **Копировать ошибку**. Текст ограничен 8 000 символами; известные форматы ключей, токенов и паролей скрываются перед сохранением. Вывод успешных инструментов и рассуждения не сохраняются. Старые служебные сообщения также отображаются в логах; текст ошибок и дополнительные детали для них восстановить нельзя. На узком экране части карточки располагаются друг под другом.

В комментариях пользователя и агента поддерживается Markdown: заголовки, **жирный текст**, *курсив*, зачёркивание, списки, цитаты, ссылки, таблицы и блоки кода. Переносы строк обычного текста сохраняются. Форматирование применяется и к уже сохранённым сообщениям; HTML-теги показываются как текст.

Агент может читать задачи через MCP: `get_task` возвращает описание, `list_comments` — обсуждение с вложениями. Для другой задачи укажите `task_id` — полный UUID или короткий ID из интерфейса, например `D91B14AC`. Этот же ID передаётся в `list_attachments`, `read_attachment` и `view_attachment` для чтения файлов и просмотра изображений той задачи. Публикации и коммиты остаются в текущей задаче. Подробности и постраничное чтение — в [документации MCP и вложений](docs/attachments.md#mcp-для-codex-и-claude-code).

Через MCP можно также управлять приложением: создавать, редактировать, архивировать и восстанавливать карточки, назначать работников и теги, запускать и продолжать работу, управлять инструкциями, моделями, автопилотом и настройками, создавать и восстанавливать бэкапы базы. Например, задайте агенту «создай карточки по этому плану и сделай бэкап». Команды используют штатные проверки приложения и сохраняют квитанции для повторных запросов без дублирования карточек. Новые карточки по умолчанию создаются в исходном проекте с ручным запуском. Полный набор инструментов и примеры — в [управлении приложением через MCP](docs/attachments.md#управление-приложением-через-mcp).

Во вкладке **Изменения** выберите запуск, чтобы увидеть diff файлов проекта: добавленные и удалённые строки, их номера и число изменений. Во время работы diff обновляется автоматически, а открытые и свёрнутые файлы остаются в прежнем состоянии; его также можно обновить кнопкой. Кнопка паузы останавливает автообновление, чтобы спокойно прочитать код: новые изменения агента появятся после нажатия «Показать» или снятия паузы. Снимок учитывает новые файлы и незакоммиченные изменения, исключает служебные вложения задачи и сохраняется в локальной SQLite вместе с кодом. Дополнительный запрос имеет собственный diff; последующая работа не меняет сохранённую историю. Изменения показываются полностью, включая большие исходники и lock-файлы; пояснение выводится только для двоичных файлов, файлов больше 4 МБ, а также если запуск изменил более 1000 путей или суммарный diff превысил 16 МБ. В деморежиме и для старых запусков, изменения которых невозможно достоверно восстановить, отображается причина недоступности diff.

## Дополнительные запросы в обсуждении

После завершения запуска напишите сообщение, при необходимости приложите файлы и нажмите **Отправить агенту**. Можно отправить только вложения. Перед отправкой видно, какой работник и какая сохранённая сессия получат запрос. Обычная заметка сама по себе ничего не запускает.

Если обычная (не сложная) задача остановилась со статусом «Заблокировано», так же можно передать агенту указания в его сохранённую сессию, например разрешить пропустить недоступную проверку. Сообщение не выдаёт CLI дополнительных разрешений; изменения из worktree попадут на слияние, когда продолжение завершится. Для заблокированного этапа сложной задачи используйте повтор или отмену.

Кнопки **Запустить снова** у завершённой задачи нет. После первого успешного завершения ручной запуск той же задачи с чистой сессией запрещён и в API: дополнительные изменения отправляются в обсуждении. Для самостоятельной новой работы создайте другую задачу. Первый запуск, повтор ещё не завершённого этапа и ответы на вопросы доступны как прежде. Уже настроенное интервальное расписание продолжает создавать плановые запуски; чтобы остановить его, поставьте расписание на паузу.

- Дополнительный запрос создаёт отдельную запись в истории и использует **точный ID прежней CLI-сессии**. Исходный результат, время завершения и история попыток сохраняются. Новый запрос, сообщения и файлы результата относятся к новой записи.
- Для сложной задачи по умолчанию выбран работник последнего завершённого этапа; можно выбрать другой завершённый этап. Продолжается только выбранная сессия. Цепочка этапов заново не запускается, прежние галочки и результаты остаются в истории. Выбор доступен для полностью завершённых запусков.
- Сохраняются исходная цель, рабочая папка, профиль работника, провайдер, запрошенная модель, усилия, режим ultracode, личные и общие инструкции, а также контекст выбранного этапа. Изменённый позже профиль или шаблон задачи применится к отдельному новому запуску, но не к этому продолжению. Для значений «по умолчанию CLI» сохраняется отсутствие переопределения; действующие настройки самого CLI остаются под контролем провайдера.
- Входные файлы исходной работы и её опубликованные результаты доступны вместе с вложениями нового запроса. Для выбранного этапа сохраняется набор его последнего хода и собственные результаты; файлы последующих этапов и посторонних заметок не подмешиваются. Если нужен такой файл, явно приложите его к запросу.
- На одну задачу одновременно выполняется один запуск. Повтор той же отправки после потерянного ответа не создаёт второй запрос; идентификатор отправки сохраняется на сервере вместе с результатом. Планировщик учитывает занятость задачи.
- Если ID сессии отсутствует, продолжение недоступно. Если сессия удалена или не принимается CLI, появляется ошибка: brigd не подменяет её новой сессией и не обещает восстановление утраченного контекста. Для отдельной работы создайте новую задачу и явно передайте необходимый контекст.
- Новый вопрос агента можно уточнить через **Продолжить работу** в той же сессии. Ошибка или блокировка дополнительного запроса не запускает автоматический повтор. После сбоя сервиса нужно подтвердить остановку старого CLI-процесса перед продолжением или отменой. Уже выполненные изменения файлов не откатываются.

Для API: `POST /api/tasks/:id/followups` принимает `sourceRunId`, `sourceStepIndex` (индекс этапа с нуля или `null` для обычного запуска), `body`, `attachmentIds` и уникальный `requestId`. Повторяйте тот же `requestId` только с тем же содержимым; изменение содержимого с прежним ID возвращает `409`. В ответе у нового запуска `trigger: "followup"` и снимок `followup` со ссылкой на источник. Обычный маршрут `/comments` сохраняет только заметку.

## Архив задач

Ненужную на доске задачу можно убрать значком архива внизу карточки, не открывая её, или кнопкой **В архив** в открытой задаче. Архивные задачи собраны на странице **Архив** (кнопка над **Настройками**), там же есть поиск и кнопка **Восстановить**.

- В архив переносится только задача без активного запуска. Запуск в работе, ожидающий ответа, прерванный или остановленный этап сложной задачи сначала завершите или отмените.
- Архивная задача не показывается на доске и не запускается по расписанию. Её можно открыть и посмотреть историю, комментарии, логи и файлы, но изменить, запустить, прокомментировать или продолжить нельзя до восстановления.
- После восстановления задача возвращается на доску с прежними настройками. Плановые запуски, время которых прошло в архиве, не выполняются задним числом: расписание продолжается со следующего срока.

Для API: `POST /api/tasks/:id/archive` и `POST /api/tasks/:id/restore`. Повторный вызов ничего не меняет. У задачи поле `archivedAt` содержит время переноса в архив или `null`. Изменение, запуск, заметка и дополнительный запрос архивной задачи возвращают `409`.

### Удаление задач

Задачу без активного запуска можно удалить навсегда кнопкой **Удалить** в открытой задаче или в строке архива. Кнопка **Удалить все** на странице **Архив** удаляет все задачи, которые были в архиве на момент подтверждения; задача, перенесённая в архив позже, остаётся.

- Вместе с задачей удаляются её запуски, обсуждение, логи, вложения и теги задачи; восстановить их можно только из бэкапа. Сами теги, работники и другие задачи не меняются. Блок задачи в документации показывает «Задача недоступна».
- Рабочие папки запусков не удаляются сразу: очистка в **Настройки → Хранилище** показывает их как «Задача удалена» и освобождает. Ветки `brigd/run-<ID>` в проекте сохраняются, если их результат не перенесён в целевую ветку.
- Задачу с активным запуском или незавершённым слиянием удалить нельзя: сначала завершите или отмените работу. При очистке архива такие задачи пропускаются, ответ сообщает их количество.

Для API: `POST /api/tasks/:id/purge` удаляет задачу; `POST /api/archive/purge` с полем `archivedBefore` (время в миллисекундах) удаляет задачи, перенесённые в архив не позже этого момента, и возвращает `deleted` и `skipped`.

## Теги

Во вкладке **Теги** можно создавать, изменять и удалять собственные теги. Для каждого тега выбирайте цвет из палитры или задавайте свой; цвет показывается в списке тегов, при назначении и на задачах. Назначайте несколько тегов при создании или редактировании задачи либо кнопкой **Изменить теги** в её карточке. Теги сохраняются в SQLite и видны на доске, в списке и в архиве.

Фильтр **Все теги** позволяет выбрать отдельный тег или задачи **Без тегов**; он работает вместе с поиском и остальными фильтрами. Изменение названия или цвета обновляет тег во всех задачах. Удаление снимает тег со всех задач. Назначение тегов доступно и во время выполнения задачи; архивную задачу сначала нужно восстановить. Лимиты: 100 тегов, до 50 символов в названии; одинаковые названия без учёта регистра запрещены.

Для API: `GET/POST /api/tags`, `GET/PATCH/DELETE /api/tags/:id`, создание принимает `{ "name": "Сайт", "color": "#3b82f6" }`. Цвет необязателен при создании; значение по умолчанию — `#7764cf`, в том числе для ранее созданных тегов. `PATCH` принимает название, цвет или оба поля, сохраняя пропущенные значения. Цвет задаётся шестизначным HEX. Для назначения используйте `PATCH /api/tasks/:id/tags` с `{ "tagIds": ["id"] }` или поле `tagIds` при создании/редактировании задачи. Пустой массив снимает все теги; отсутствие поля при редактировании сохраняет назначения. Ответ задачи содержит `tagIds` и `tags`; `GET /api/tasks?tagId=id` возвращает задачи с выбранным тегом.

## Работники

В разделе **Работники** создайте профиль: имя, **Описание**, аватар, **Провайдер** (Codex или Claude Code), конкретная **Модель**, уровень усилий, чекбокс **ultracode** и необязательные **Личные инструкции**. В форме задачи назначьте работника; провайдер и модель берутся из его профиля. Без работника можно по-прежнему выбрать CLI напрямую и использовать его модель по умолчанию.

- Имя, описание и аватар помогают узнавать исполнителя в задачах и истории. **Описание** — до 1 000 символов; оно показывается рядом с именем в списке работников, карточках задач, назначении, комментариях и истории этапов. Это текст для интерфейса: он не передаётся агенту как инструкция. Пустое описание не подменяется личными инструкциями.
- Чекбокс **ultracode** включает нативный режим агента: у Codex — `model_reasoning_effort="ultra"` с включёнными подагентами вместо выбранного уровня усилий; у Claude Code — `--settings '{"ultracode":true}'`, при этом выбранный уровень усилий сохраняется. У Claude Code нужен CLI 2.1.284 или новее; доступность режима также зависит от модели и настроек провайдера. При неподдерживаемом CLI включённый режим возвращает ошибку запуска. Снятый чекбокс возвращает Codex к обычным настройкам усилий и отключает ultracode в поддерживаемом Claude Code. В API профиля поле `ultracode` принимает `true` или `false`; по умолчанию выключено. Чекбокс **ultracode** в карточке задачи переопределяет профиль для новых запусков этой задачи: поставленная или снятая вручную галочка действует независимо от настроек работника, у сложной задачи — на всех этапах; нетронутая галочка следует профилю. Для API: в `POST /api/tasks` и `PATCH /api/tasks/:id` поле `ultracode` принимает `true`, `false` или `null`; по умолчанию `null` — по профилю работника. `PATCH` без этого поля сохраняет значение, явный `null` возвращает задачу к профилю; другие значения возвращают `400`. Инструменты MCP `create_task` и `update_task` принимают то же поле в `data`. Ответ задачи и запуска содержит `ultracode` (`null`, если режим берётся из профиля).
- **Замена при лимитах** — работник, который подхватит новую сессию, если CLI этого профиля сообщит об исчерпании лимитов использования. Пустое значение означает общую настройку из **Настройки → Общие** (там же описаны правила замены); выбрать самого себя нельзя, архивный работник не подходит для нового выбора, а уже сохранённая замена переживает его архивирование, но не сработает, пока работника не восстановят. В API профиля поле `fallbackWorkerId` принимает ID активного работника или `null`; инструменты MCP `create_worker` и `update_worker` принимают то же поле. Снимок запуска это поле не содержит: замена выбирается по актуальному профилю в момент ошибки.
- При первом запуске в каталог добавляются Sol 6.1 (`gpt-6.1-sol`), Astra (`gpt-6-astra`) и Luna (`gpt-6-luna`) для Codex; Opus 5.5 (`claude-opus-5-5`), Sonnet 5.5 (`claude-sonnet-5-5`) и Haiku 5.5 (`claude-haiku-5-5`) для Claude Code. Это проверенные ID, а не список моделей, доступных вашему аккаунту. Вариант **Другая модель…** позволяет ввести ID новой модели или нативный alias без обновления brigd. ID — до 128 символов, без пробелов, управляющих символов и CLI-флагов; допускаются точки, подчёркивания, дефисы, двоеточия, слэши, `+`, `@` и квадратные скобки.
- **По умолчанию CLI** в поле модели не добавляет `--model` и сохраняет нативные настройки. Явный ID передаётся отдельным аргументом `--model ID` в новых запусках и при продолжении точной сессии; shell не используется. Перед запуском brigd проверяет поддержку флага на обоих путях. При отказе CLI ошибка показывает запрошенные модель/усилия; brigd не выбирает другую модель автоматически. Доступность и фактическое исполнение по-прежнему зависят от CLI, аккаунта и правил провайдера. Смена провайдера в редакторе сбрасывает модель на «По умолчанию CLI».
- **Личные инструкции** — до 4 000 символов. В интерфейсе их можно увидеть и изменить только в профиле работника; в карточках задач, списках и истории они не отображаются. Они по-прежнему передаются CLI внутри обычного текста задания как JSON-строка с пометкой недоверенного необязательного предпочтения. Они не меняют задачу, формат результата или нативные разрешения CLI. Не помещайте в профиль пароли и другие секреты. Это разделение отображения, а не контроль доступа: локальная база и API сохраняют инструкции для выполнения и продолжения сессий.
- **По умолчанию CLI** не добавляет флаг усилий и сохраняет настройки провайдера. Codex поддерживает выбор `low`, `medium`, `high`, `xhigh`; Claude Code — `low`, `medium`, `high`, `xhigh`, `max`. brigd передаёт Codex параметр `-c model_reasoning_effort="…"`, Claude — `--effort …`, без замены одного уровня другим.
- Перед запуском проверяется помощь установленного CLI. Явный уровень усилий для Codex требует `--config` и `--strict-config` на путях нового запуска и продолжения; строгая проверка включается, чтобы неизвестная настройка не была проигнорирована. Для Claude проверяются `--effort` и перечисленные им уровни. Если поддержки нет, запуск завершится понятной ошибкой: обновите CLI или выберите уровень по умолчанию.
- Выбранный уровень — запрос к CLI. Фактические возможности зависят от модели, аккаунта и настроек провайдера. В частности, Claude может ограничить уровень согласно модели или правилам организации, в том числе без отдельного уведомления в `stream-json`. brigd не меняет модель или лимиты аккаунта и не обещает одинаковую глубину работы разных моделей.
- Аватар загружается локально: выберите PNG, JPEG или WebP до 5 МБ, настройте масштаб (25–300%) и область с помощью перетаскивания или ползунков. Предпросмотр показывает сохранённый результат; «Сбросить кадрирование» возвращает масштаб 100% и центр изображения. Уже загруженный аватар можно открыть кнопкой «Изменить размер аватара» без выбора нового файла. Выбранная квадратная область сохраняется в 256 × 256 px только при сохранении профиля; отмена закрывает черновик без загрузки. Для повторного кадрирования доступно сохранённое изображение; исходный файл можно загрузить заново. При обычном изменении профиля аватар сохраняется без обработки; сервер принимает PNG, JPEG или WebP до 256 КиБ, размером не более 1024 × 1024. Байты сохраняются в той же SQLite, без внешнего хостинга. Смена аватара не изменяет фото в старых запусках; внешние URL и SVG не используются.
- **Интегратор** — единственный встроенный работник: он не назначается задачам и не архивируется, а запускается сам при конфликте слияния. У него один редактируемый профиль в карточке раздела: по умолчанию провайдер, модель и усилия берутся **как у запуска**, результат которого объединяется; режим **свои** фиксирует выбранный CLI для всех конфликтов. Там же задаются **Указания Интегратору** (до 4 000 символов, передаются ему при разрешении конфликта так же, как личные инструкции работника, и нигде больше не показываются) и аватар. Merge-коммиты brigd подписывает автором «Интегратор». API: `GET/PATCH /api/integrator`. Подробности — в [регламенте при конфликте](docs/execution.md#интегратор-регламент-при-конфликте-слияния).
- Архив скрывает работника из нового назначения. Уже назначенные задачи и их расписание продолжают работать; работника можно восстановить. Чтобы остановить будущие запуски, отдельно поставьте расписание задачи на паузу.
- Кнопка **Удалить** в карточке работника удаляет профиль навсегда. Работника, назначенного в задачах (в том числе архивных и в этапах сложных задач), сначала замените в них или удалите эти задачи. Выбор этого работника заменой при лимитах или работником по умолчанию очищается. История прошлых запусков сохраняет его снимок, и их сессии можно продолжать. API: `POST /api/workers/:id/purge`; `DELETE /api/workers/:id` по-прежнему переносит работника в архив.

При старте сохраняется неизменяемый снимок имени, описания, аватара, провайдера, запрошенной модели, уровня усилий, режима ultracode и личных инструкций. Для сложной задачи сразу фиксируются профили **всех** этапов, включая будущие. Продолжение после вопроса, повтор этапа или перезапуск сервиса использует тот же снимок. Редактирование и архивирование профиля не меняют уже начатый запуск; следующий новый запуск использует актуальные настройки назначенного работника. Выбор режима ultracode в карточке задачи так же фиксируется в запуске при старте: продолжение после вопроса, повтор этапа и дополнительный запрос из обсуждения сохраняют его, а изменение галочки в карточке действует со следующего запуска. Для модели или усилий «по умолчанию CLI» фиксируется отсутствие переопределения, а не внутренние настройки провайдера. Нативные aliases могут менять своё значение; конкретные ID фиксируют запрошенную модель точнее. Существующие профили и старые снимки без модели получают значение `null` (CLI default); миграция добавляет nullable-колонку без удаления данных. У старых работников и снимков описание остаётся пустым: тексты личных инструкций сохраняются без изменений и не копируются в описание. У старых профилей и снимков режим ultracode выключен. Существующие карточки и запуски без собственного выбора ultracode по-прежнему следуют профилю работника: миграция добавляет nullable-колонки `ultracode` в таблицы задач и запусков, где `null` означает «по профилю». Открытие базы не переписывает старые JSON-снимки.

Поддержка параметров сверена с [моделями Codex](https://learn.chatgpt.com/docs/models), [конфигурацией Codex](https://learn.chatgpt.com/docs/config-file/config-reference), [CLI Claude Code](https://code.claude.com/docs/en/cli-reference) и [моделями и effort в Claude](https://code.claude.com/docs/en/model-config). Предустановленные ID и разбор флагов проверены для Codex 0.162.0 / Claude Code 2.1.295. Проверка `--help` не вызывает модель и не проверяет доступность модели или уровня на вашем аккаунте. Для ручной проверки всех сочетаний model/effort/new/resume/MCP без вызова модели: `bun scripts/check-cli.ts` (нужны оба CLI на PATH).

### Каталог моделей в настройках

Откройте **Настройки** → **Модели**. Для Codex и Claude Code можно добавлять, редактировать и удалять записи: провайдер, понятное название (до 80 символов) и точный ID модели. Профили работников берут варианты выбора из этого списка. В одном провайдере нельзя сохранить два одинаковых ID; допускается до 100 записей на провайдера.

Каталог хранится в локальной SQLite и сохраняется после перезапуска. Стандартные записи создаются только один раз: удалённые модели не возвращаются автоматически, даже если список опустел. Изменение ID, перенос записи к другому провайдеру или удаление из каталога **не меняют** сохранённые профили и уже начатые запуски. В профиле хранится сам ID; если его больше нет в списке, он остаётся выбранным как «Другая модель…». Чтобы перевести работника на другой ID, отредактируйте его профиль отдельно. Ни изменение каталога, ни ручной ввод не проверяют доступ к модели и не вызывают платный запрос.

API каталога: `GET/POST /api/models`, `GET/PATCH/DELETE /api/models/:id`. Поля записи: `provider`, `modelId`, `label`; сервер также возвращает `id`, `createdAt`, `updatedAt`. Мутации используют те же ограничения Origin/Host и размер JSON, что остальные настройки; изменение каталога не предоставляет нативных разрешений агенту.

## Инструкции

Раздел **Инструкции** в боковом меню хранит общие указания для агентов: например, язык ответа, порядок проверки проекта или требования к отчёту. Добавьте название и текст, затем включите инструкцию. Все включённые инструкции передаются Codex и Claude Code при каждом **новом** ручном или плановом запуске любой задачи, в том числе без назначенного работника.

- Можно создавать, редактировать, включать, выключать и удалять инструкции. Порядок применения — порядок создания; редактирование и переключение его не меняют.
- В начале запуска сохраняется отдельная копия названий и текстов включённых инструкций. Во вкладке **Запуски** можно открыть именно эту копию. Редактирование, выключение или удаление записи из библиотеки не меняет уже начатую сессию, её продолжения и историю. Следующий запуск получает актуальный набор.
- Запуски, созданные до обновления, сохраняют пустой набор общих инструкций. Миграция SQLite добавляет новые данные, не удаляя задачи, комментарии, работников или сессии.
- Название — до 140 символов, текст — до 16 000, библиотека — до 100 записей. Для включённого набора дополнительно ограничены общий текст (64 000 символов) и размер передаваемого JSON (24 000 байт UTF-8, включая служебные поля). Русский текст и экранируемые символы занимают больше байт. При превышении сократите текст или выключите часть записей; brigd ничего не обрезает. Большую инструкцию можно сохранить выключенной.
- Общие инструкции дополняют задание и личные инструкции работника. Они передаются как явно обозначенные JSON-данные внутри обычного задания, не как системная политика. Они не могут отменять конкретную задачу, формат результата, ограничения безопасности или нативные разрешения CLI. Это также не способ запустить shell-команду вне обычной работы агента.
- Текст и снимки хранятся в локальной SQLite; при реальном запуске текст передаётся выбранному CLI и его провайдеру. Не добавляйте пароли и другие секреты. Удаление инструкции из списка не удаляет её исторические копии в запусках.

Демо-режим сохраняет и показывает тот же снимок, но не обращается к модели и не исполняет произвольные указания.

## Документация

Раздел **Документация** в боковом меню хранит страницы в духе Notion: слева оглавление с деревом страниц и поиском, справа редактор из блоков. Это справочный материал: если он нужен в задаче, вставьте ссылку на страницу в её описание. Агенты читают страницы через MCP.

- Страницы вкладываются друг в друга до 8 уровней. Их можно перетаскивать в оглавлении: на верхнюю или нижнюю кромку строки для перестановки, в середину для вложения. В меню страницы доступны подстраница, перемещение выше и ниже, вложение в предыдущую, вынос на уровень выше и корзина. Под открытой страницей оглавление показывает её заголовки; щелчок переводит к нужному блоку. Поиск над деревом ищет по названиям и тексту блоков.
- Типы блоков: текст, заголовки трёх уровней, маркированный и нумерованный списки, чекбокс, раскрывающийся блок, цитата, выноска с иконкой и цветом, код с подписью языка, таблица, изображение, задача, оглавление и разделитель. Символ `/` в начале пустого блока открывает меню типов; Markdown-префиксы `# `, `- `, `1. `, `[] `, `> `, ```` ``` ```` и `---` меняют тип на ходу. Enter создаёт следующий блок, Shift+Enter переносит строку, Tab и Shift+Tab меняют вложенность любого блока, Alt+↑/↓ переставляют блок, Ctrl+B, Ctrl+I и Ctrl+E оборачивают выделение. Блок можно перетащить за ручку слева или открыть по ней меню действий. Ctrl+Z и Ctrl+Shift+Z отменяют и возвращают структурные правки: удаление, разбиение, перемещение и смену типа; набор текста внутри блока отменяет сам браузер.
- Раскрывающийся блок скрывает блоки, вложенные глубже него. Таблица редактируется по ячейкам: Enter переходит на строку ниже и добавляет новую в конце, Tab идёт по ячейкам, под таблицей есть кнопки строк и столбцов. Изображения PNG, JPEG, WebP и GIF до 10 МиБ хранятся вместе со страницей, до 50 на страницу; картинка, убранная со страницы, удаляется через час. Блок задачи показывает карточку со статусом и открывает её по кнопке. Оглавление внутри страницы собирает её заголовки.
- Текст блока хранится как inline-Markdown: `**жирный**`, `*курсив*`, `` `код` ``, ссылки и зачёркивание. В фокусе блок показывает исходный текст, без фокуса рендерится. HTML не допускается, как в комментариях.
- Изменения сохраняются автоматически через секунду после паузы, при переходе на другую страницу и при закрытии вкладки. Если та же страница изменилась в другом окне или через MCP, редактор сообщает о конфликте и предлагает загрузить новую версию; свои правки нужно повторить.
- Кнопка **Удалить страницу** под названием открытой страницы и пункт **В корзину** в её меню переносят страницу в **Корзину** внизу оглавления вместе с подстраницами; оттуда, а также кнопками на самой странице из корзины, её можно восстановить или удалить навсегда вместе с изображениями. Страница из корзины открывается только для чтения. Если родительская страница ещё в корзине, восстановленная страница становится страницей верхнего уровня.
- В форме задачи блок **Документация** прикрепляет до 20 страниц. Карточка показывает их ссылками, а каждый запуск сохраняет названия страниц на момент старта. Агент получает в задании список идентификаторов и читает актуальное содержимое инструментом `get_doc_page`; содержимое страниц не является инструкциями или разрешениями. Страница, попавшая в корзину, из списка пропадает, но ссылка в задаче сохраняется до восстановления.
- Лимиты: название до 140 символов, текст блока до 16 000, ячейка таблицы до 2 000, до 100 строк и 20 столбцов, до 2 000 блоков и 512 КиБ на странице, до 5 000 страниц вместе с корзиной, хранилище изображений до 1 ГиБ. Страницы и картинки хранятся в той же SQLite и входят в бэкапы; восстановление базы без этих таблиц просто создаёт их пустыми, а поисковый индекс строится заново при запуске.
- Ссылка на страницу вида `http://127.0.0.1:4310/#/docs/<id>` открывает её сразу. Для API: `GET /api/docs`, `GET /api/docs/trash` и `GET /api/docs/search?q=` возвращают списки, `POST /api/docs` создаёт страницу с `title`, `parentId` и необязательным `markdown`, `GET /api/docs/:id` читает блоки, `PUT /api/docs/:id` сохраняет `title`, `blocks` и `version` (при устаревшей версии `409`), `PUT /api/docs/:id/markdown` заменяет содержимое из Markdown, `GET /api/docs/:id/export` отдаёт Markdown, `PATCH /api/docs/:id` принимает `parentId` и `position`, `POST /api/docs/:id/images?name=` загружает картинку, `GET /api/docs/:id/images/:imageId` отдаёт её, `DELETE /api/docs/:id` переносит в корзину, `POST /api/docs/:id/restore` и `POST /api/docs/:id/purge` восстанавливают и удаляют окончательно. Инструменты MCP для агентов описаны в [управлении приложением через MCP](docs/attachments.md#управление-приложением-через-mcp).

## Что умеет MVP

- Все задачи во вкладке «Задачи»: доска и список, поиск, фильтрация по агенту, статусу, расписанию и тегам; задачи с ошибками, блокировками, конфликтами слияния, прерванные и отменённые собраны в плашке «Проблемные задачи» над доской, раскрытой по умолчанию
- Собственные теги с назначением нескольких тегов одной задаче, переименованием и удалением
- Архив задач: убирает задачу с доски и из расписания, сохраняя историю; восстановление в один клик, удаление по одной или всех сразу
- Именованные работники с локальными аватарами, описанием, личными инструкциями, настройками усилий и неизменяемой историей профиля для каждого запуска
- Замена работника при исчерпании лимитов CLI: общая настройка для каждого провайдера в «Настройки → Общие» и своя замена в профиле работника; продолжения сохранённых сессий не передаются
- Библиотека общих инструкций с переключателями и неизменяемой копией текста для каждого запуска
- «Настройки» с разделами «Общие», «Язык», «Внешний вид», «Модели», «Разрешения», «Автопилот», «Параллельность», «Хранилище» и «Бэкапы»
- Интерфейс на русском и английском языках: переключатель в «Настройки → Язык»
- 13 цветовых схем: нейтральные Светлая и Тёмная и атмосферные палитры, которые различаются устройством, а не только оттенком. Светлые: Горизонт, Плакат, Лишайник, Патина, Тихая гавань; тёмные: Тёплый свет, Искра, Терминал, Сумерки, Тревога, Бункер. Выбор сохраняется в этом браузере и синхронизируется между вкладками; ранее выбранная упразднённая схема открывается ближайшей новой той же яркости
- Адаптивная раскладка для узких экранов, увеличенного текста и масштаба браузера
- Название, инструкция, приоритет, провайдер, рабочая папка, режим ultracode, ручной запуск, интервал или очередь автопилота, первый запуск, пауза расписания
- Раздел «Автопилот»: очередь задач разбирается без участия человека, с временем остановки, предохранителем от серии ошибок и итогами сессии, включая счётчики разбора упавших проверок
- Разбор упавшей проверки слияния: повтор, проверка целевой ветки и автоматический возврат работнику по кодам возврата, с этапами в карточке
- Раздел настроек «Разрешения»: общий переключатель **Полный доступ Codex и Claude Code**, включённый по умолчанию. Оба CLI работают без подтверждений и собственных песочниц, с правами пользователя сервиса; настройка сохраняется и применяется к новым запускам и продолжениям. После выключения доступны пути к пользовательским конфигам и кнопки **Настроить разрешения…** для ограниченного режима. Кнопка **Инструкция** показывает [docs/cli-permissions.md](docs/cli-permissions.md).
- Карточка с комментариями, вопросами, результатами и отдельной историей запусков
- Учёт расхода: для каждого хода агента сохраняются токены, стоимость (если CLI её сообщает) и длительность. Во вкладке «Запуски» карточки — строка вида «12,3 тыс. токенов · $0,42 · 7 мин» для каждого хода и сумма по запуску, в «Автопилоте» — сумма за сессию, в карточке работника — за 30 дней и за всё время ([подробнее](docs/execution.md#учёт-расхода))
- Мгновенное обновление открытых вкладок через поток событий вместо частого опроса сервера
- Статус выполнения, который агент задаёт сам во время работы («Сбор информации о проекте», «Написание кода»), на карточке, в списке и в открытой задаче ([подробнее](docs/attachments.md#статус-выполнения))
- Дополнительные запросы из обсуждения в выбранную завершённую сессию, с отдельной историей и сохранением контекста работника/этапа
- Продолжение **точной** сессии Codex/Claude, отмена активного запуска
- SQLite WAL, атомарный захват планового запуска и уникальность «задача + плановое время»
- Один незавершённый запуск на задачу, включая ожидание ответа и прерывание
- Восстановление после перезапуска без автоматического повтора потенциально выполненных действий
- Демо-адаптер, автоматические тесты и браузерные сценарии

## Расписание и восстановление

Интервалы отсчитываются от первого запуска. Если сервис спал несколько часов, выполняется максимум **один последний актуальный** интервал; пропущенная очередь не догоняется. Если задача уже выполняется или ждёт ответа, её очередные интервалы пропускаются. Ещё не начавшийся плановый запрос остаётся в очереди и обновляется до последнего актуального интервала.

Пауза останавливает будущие автоматические запуски. Активный запуск она не отменяет; ручной запуск по-прежнему доступен. Изменения инструкции задачи, библиотеки общих инструкций, папки, провайдера, режима ultracode, назначения и профиля работника применяются только к новым запускам. Текущий запуск хранит собственный снимок настроек.

После остановки сервиса выполнявшиеся задачи помечаются как **Прервано**. Они не запускаются автоматически. Если ID сессии уже сохранён, можно продолжить после явного подтверждения, что старый CLI-процесс остановлен. После аварийного завершения процесса brigd проверьте это самостоятельно: осиротевший CLI может ещё работать. Если ID не успел сохраниться, отмените прерванный запуск и начните новый после проверки результатов. Ожидающие ответа сессии переживают перезапуск без потери состояния.

Отмена переводит запуск в **Останавливается** и отправляет сигнал CLI (на POSIX — группе процессов). До завершения остановки задача остаётся занята; затем статус меняется на **Отменено**. Уже выполненные изменения не откатываются. Новые реальные работы выполняются в отдельных Git worktree. Единая очередь ограничивает число агентов на репозиторий, затем последовательно проверяет объединённый код и переносит результат в чистую целевую ветку. Конфликты и ошибки проверки видны в карточке. Конфликт слияния по умолчанию разрешает встроенный работник **Интегратор**: brigd объединяет целевую ветку в worktree задачи, агент правит конфликтующие файлы, brigd создаёт merge-коммит и повторяет проверку; при повторных конфликтах не больше трёх кругов, затем кнопка **Поручить интегратору** или ручное решение. Упавшую проверку brigd по умолчанию разбирает сам, без модели, по кодам возврата: один раз повторяет команду в том же кандидате (если прошла — слияние продолжается, а карточка получает пометку «Проверка прошла со второй попытки»), затем выполняет её на текущей вершине целевой ветки в отдельном чистом worktree (если падает и там — задача не возвращается: сломана целевая ветка) и иначе сам отправляет дополнительный запрос в сохранённую сессию работника с концом вывода как недоверенными данными — не больше трёх раз на результат, повторы и проверка целевой ветки вместе не дольше 30 минут. Задачи с этапами автоматически не возвращаются. Переключатель — в **Настройки → Автопилот**, подробности — в [разборе упавшей проверки](docs/execution.md#разбор-упавшей-проверки). В ограниченном режиме песочница Codex защищает `.git` от записи; коммит можно создать через инструмент brigd `commit_changes`. Полный доступ отключает эту защиту CLI. Коммиты brigd называются по задаче (`brigd: <название задачи>`, `brigd: объединение «<название задачи>»`), а ID запуска хранится в трейлере `Brigd-Run: <ID>`: `git log --grep='Brigd-Run: <ID>'` находит коммиты запуска. Подробности, ограничения инструмента коммитов и настройка команд — в [инструкции очереди и слияний](docs/execution.md).

## Автопилот

Раздел **Автопилот** разбирает очередь задач без вашего участия, например ночью. В форме задачи выберите режим **Автопилот** вместо ручного запуска или интервала: задача встаёт в очередь и ждёт, пока автопилот включён, подошла её очередь и есть свободное место. Первой запускается задача в начале очереди. Очередь сгруппирована по приоритету: сначала **Критический**, затем **Высокий**, **Обычный** и **Низкий**, поэтому задача с более высоким приоритетом берётся в работу раньше независимо от того, когда её создали. Новые задачи и задачи, переключённые в режим автопилота, встают в конец своего приоритета; смена приоритета переносит задачу в конец нового. Порядок внутри одного приоритета меняется перетаскиванием строк в разделе **Автопилот** или стрелками ↑ и ↓ на значке перемещения; поставить задачу выше задач более высокого приоритета можно только повысив её приоритет. Задача занятого репозитория пропускается, пока он занят, а задачи других репозиториев её не ждут. Кнопка **Отложить** (пауза задачи) оставляет режим автопилота, но не даёт взять задачу; **Вернуть в очередь** снимает паузу, и задача возвращается на прежнее место. В **Итогах сессии** не показываются задачи, перенесённые в архив.

Включите автопилот кнопкой в разделе и при желании укажите время остановки, например 08:00. Пока он включён, планировщик каждую секунду проверяет очередь и запускает следующую задачу только при свободном месте по лимитам **Настройки → Параллельность** (всего процессов и задач в одном репозитории): задачи не ставятся в очередь заранее и остаются редактируемыми до старта, а выключение ничего не отменяет. Результат проходит обычную проверку и слияние, конфликты разрешает Интегратор, а упавшую проверку brigd разбирает сам и при необходимости возвращает задачу работнику. При лимите 1 задача на репозиторий следующая задача начинается после слияния предыдущей, поэтому серия задач накапливает результат, а не конфликты; при большем лимите задачи одного репозитория идут параллельно в своих worktree, а их результаты по одному проходят проверку и слияние.

Правила сессии (сессия начинается при включении):

- Каждая задача берётся один раз за сессию. Ошибка, блокировка и вопрос агента ждут вашего возвращения; задача с вопросом остаётся занятой, автопилот берёт следующую. Повтор возможен вручную или в следующей сессии.
- Предохранитель: три запуска подряд со статусом ошибки или блокировки выключают автопилот, причина показывается в разделе, а в карточке последней задачи появляется системный комментарий. Так разлогиненный CLI или лимит аккаунта не прогоняют всю очередь впустую. Исчерпанный лимит автоматических возвратов после упавшей проверки считается так же, как ошибка. Успешный результат или вопрос сбрасывают счётчик. Если настроена замена при лимитах, задача сначала передаётся работнику замены в новой сессии, и такой ход не считается ошибкой; ошибкой станет только лимит у самой замены.
- После времени остановки новые задачи не берутся; начатые запуски и их слияние доделываются.
- Перезапуск сервиса выключает автопилот: прерванные запуски требуют проверки человеком, как и всегда.
- Раздел показывает очередь, отложенные задачи и итоги сессии: сколько готово, где нужен ответ, где ошибка или проблема слияния, итоги разбора упавших проверок (прошли со второй попытки, целевая ветка не прошла, возвращено работникам, исчерпан лимит возвратов) и расход за сессию: токены, стоимость и время ходов её задач. В истории такие запуски отмечены как «Автопилот», на доске есть фильтр «Автопилот».

Перед реальным запуском сохраните **BRIGD_INTEGRATION_CHECKS** в **Настройки → Автопилот**: например, `[["bun","install","--frozen-lockfile"],["bun","run","verify"]]`. Без явно заданных команд ручные, интервальные запуски, автопилот, продолжения и слияния заблокированы. Настройка применяется без перезапуска и имеет приоритет над переменной окружения; mock-режиму она не нужна.

Перед ночной сессией: проверьте режим доступа в **Настройки → Разрешения**. Полный доступ включён по умолчанию; для ограниченного режима настройте правила CLI по [docs/cli-permissions.md](docs/cli-permissions.md). Оставьте целевую ветку чистой, проверьте наличие команд проверки, отключите сон компьютера и подумайте об общей инструкции «принимай разумные решения вместо вопросов». API: `GET/PATCH /api/autopilot` с полями `enabled` и `until` (время в миллисекундах или `null`). Подробности — в [инструкции очереди](docs/execution.md#автопилот-разбор-очереди-без-участия-человека).

## Поток событий интерфейса

Открытая вкладка держит одно подключение Server-Sent Events `GET /api/events` и перечитывает данные только тогда, когда сервер сообщает об изменении. Первое событие `ready` содержит `{ "instance": "<ID открытой базы>", "revision": <число> }`. Дальше событие `change` с `{ "revision": <число>, "scopes": [...] }` приходит после записи в базу; изменения за 100 мс объединяются в одно событие. Разделы: `tasks` (задачи, запуски, комментарии, логи, вложения, слияния), `autopilot`, `instructions`, `docs`, `workers` (включая профиль Интегратора), `tags`, `settings` (в том числе каталог моделей) и `backups`. Раз в 15 секунд сервер отправляет комментарий-heartbeat. Ревизия считает записи с открытия базы, поэтому после перезапуска сервиса или восстановления бэкапа меняется `instance`.

При восстановлении бэкапа и остановке сервиса сервер закрывает все потоки. Клиент переподключается сам: через секунду после обрыва работавшего потока, затем с удвоением задержки до 15 секунд. Если первая попытка не удалась, вкладка сразу перечитывает данные и показывает ошибку связи, не дожидаясь резервного опроса. После переподключения к другому `instance` или с пропущенными изменениями вкладка перечитывает всё. На случай недоступного потока (например, прокси буферизует ответ) вкладка дополнительно перечитывает данные раз в 20 секунд и при возвращении на вкладку. Скрытая вкладка сохраняет поток, но перечитывает данные только после возвращения на неё. Одна вкладка перечитывает один раздел не чаще раза в секунду, даже если агент пишет логи непрерывно.

## Разрешения и безопасность

- Без контейнера сервис слушает только `127.0.0.1`. В Compose он слушает `0.0.0.0` внутри контейнера, а порт хоста опубликован только на `127.0.0.1`. Не публикуйте порт в интернет и не ставьте перед ним публичный reverse proxy. Авторизации и многопользовательского режима в MVP нет.
- API проверяет `Host`, `Origin` и `Sec-Fetch-Site`; изменения принимаются из локального интерфейса. Размер JSON и загружаемых файлов ограничен; для бэкапов доступна отдельная двоичная загрузка. CORS не включён. Поток событий `GET /api/events` проходит те же проверки, передаёт только названия изменившихся разделов без данных и допускает не больше 32 одновременных подключений на сервис (сверх — `429`).
- CLI запускаются через массив аргументов `Bun.spawn`, без shell-интерполяции.
- По умолчанию включён полный доступ: Codex запускается с `--dangerously-bypass-approvals-and-sandbox`, Claude Code — с `--dangerously-skip-permissions` и отключённой песочницей. Оба CLI выполняют команды и записывают файлы с правами пользователя сервиса. Права ОС, границы контейнера, вход в аккаунты, лимиты и политики провайдеров сохраняются. Переключатель в **Настройки → Разрешения** сохраняется в базе и применяется к новым процессам, включая продолжения; уже запущенные процессы сохраняют прежний режим. API: `GET/PATCH /api/settings/permissions`, `{"mode":"full"}` или `{"mode":"standard"}`.
- При выключенном полном доступе Codex работает с `workspace-write`, сетью внутри песочницы и политикой подтверждений `on-request`; Claude Code использует обычные правила разрешений. Нативные интерактивные подтверждения CLI в карточке не поддерживаются: требующий их запуск получает **Блокировка**. Причину можно скопировать из блока **Ошибка** во вкладке **Логи**. После изменения режима или правил повторите этап либо продолжите обычную задачу дополнительным запросом. Подробности — в [docs/cli-permissions.md](docs/cli-permissions.md).
- CLI загружают свою обычную локальную/проектную конфигурацию, правила, плагины и доверенные инструменты. brigd не изолирует их от вашей конфигурации и не является границей безопасности. Используйте доверенные рабочие папки и инструкции.
- Сырой stdout/stderr, рассуждения и вывод инструментов не записываются в комментарии. Сохраняются краткие события, явные вопросы и финальный результат. Если CLI падает без разобранной ошибки (ненулевой код выхода, нет сессии или результата, строка не в формате JSONL), в блок «Ошибка» на вкладке «Логи» дополнительно попадает ограниченный хвост stderr (до 4 000 символов) и фрагмент проблемной строки с удалёнными известными форматами секретов; записи об ошибках сохраняются даже после лимита в 1 000 записей лога за ход. Не указывайте секреты в инструкции: инструкции и ответы хранятся в локальной SQLite, а при реальном запуске передаются CLI.
- По умолчанию ход агента работает до результата, ошибки или отмены. В **Настройки → Общие** можно задать «Максимальная длительность хода агента, мин» (целое 1–1440; пусто — без лимита), а в карточке — «Лимит времени, мин» (пусто — общая настройка). Значение фиксируется для каждого нового хода, включая ответ на вопрос, дополнительный запрос и Интегратора; изменения не влияют на текущий ход. По истечении лимита brigd останавливает группу процессов CLI через SIGTERM, затем SIGKILL, отмечает запуск ошибкой и сохраняет ID сессии для ручного продолжения. Такая ошибка учитывается предохранителем автопилота. Отдельная общая настройка «Максимальная длительность проверки слияния, мин» ограничивает каждую команду `BRIGD_INTEGRATION_CHECKS` и её повторы (пусто — без лимита); значение фиксируется на попытку слияния. Строка JSONL длиннее 1 МиБ (обычно огромный вывод инструмента, например поиск по всему проекту) не разбирается: brigd пропускает её, отмечает это в логах и продолжает запуск. Остальной вывод ограничен 8 МиБ суммарно; превышение — ошибка, не завершение задачи. Короткие диагностические команды проверки CLI имеют собственный тайм-аут.
- База не шифруется. По умолчанию каталог данных приватный на POSIX. Храните его в защищённом локальном профиле и делайте резервную копию при остановленном сервисе.

## CLI-протокол

Codex: `exec --json`, `thread.started` сохраняет `thread_id`, продолжение использует `exec resume` с этим ID. Claude: `-p --output-format stream-json --verbose`, сохраняется `session_id`, продолжение — `--resume` с этим ID. Адаптер проверяет установленные `--help` перед использованием флагов; JSON Schema включается, если поддерживается.

Агент завершает ход строгим объектом:

```json
{
  "status": "needs_input",
  "summary": "Нужно уточнить критерий результата.",
  "questions": ["Для какой аудитории подготовить обзор?"]
}
```

Допустимы `needs_input`, `completed`, `blocked`. Только `needs_input` содержит вопросы. Нулевой exit code сам по себе не означает успех: нужны ID сессии, финальное событие провайдера и валидный объект. Непонятный или повреждённый ответ становится видимой ошибкой протокола.

Расход хода берётся из тех же событий. Claude Code: финальное `result` — `total_cost_usd` и `usage` (`input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, `output_tokens`). Codex: `usage` в `turn.completed` (`input_tokens`, `cached_input_tokens`, `output_tokens`); стоимость Codex не сообщает, она остаётся пустой — тарифы brigd не подставляет. Длительность brigd измеряет сам, от запуска CLI до завершения хода. Все поля usage необязательны: старый CLI без них оставляет в записи только длительность, а отсутствие usage никогда не превращает успешный ход в ошибку.

Документация: [Codex non-interactive](https://learn.chatgpt.com/docs/non-interactive-mode), [Claude headless](https://code.claude.com/docs/en/headless), [Claude CLI reference](https://code.claude.com/docs/en/cli-reference).

## Разработка и тесты

```sh
bun run dev          # Vite: http://127.0.0.1:5173, API: PORT (по умолчанию 4310)
bun run dev:demo     # то же, без настоящих CLI
bun run verify      # typecheck + Bun tests + production build
bun run test        # только Bun tests: файлы идут в 8 параллельных процессах (--parallel=8)
bun run test:smoke  # HTTP, реальные процессы сервиса, restart/SIGKILL; только mock
bunx playwright install chromium
bun run test:e2e    # production browser tests, только mock
```

Браузерные тесты дополнительно проверяют сохранение и перенос темы с Trackt, синхронизацию между вкладками, недоступное хранилище браузера, размеры экрана от 320 до 1440 px, текст 200% и длинное содержимое карточек и форм.

Проверки инструкций охватывают CRUD и границы входных данных, обновление существующей базы, атомарное ограничение включённого набора, снимки ручных и плановых запусков, продолжение после изменения библиотеки, prompt для обоих CLI и безопасные аргументы. HTTP smoke проверяет библиотеку и снимки через настоящий сервис и перезапуск, используя только mock-агента. Браузерные сценарии покрывают редактор, переключатели, историю и узкие экраны в обеих темах.

Проверки профилей отдельно подтверждают миграцию пустого описания без потери личных инструкций, независимое редактирование двух полей, неизменность исторических описаний и передачу CLI только личных инструкций. В браузере проверяется отсутствие их текста вне редактора профиля, включая раскрытые этапы и историю, а также описание под именем в обеих темах.

Проверки дополнительных запросов охватывают неизменность старого результата, точный session ID, выбор этапа, замороженный профиль и инструкции, идемпотентность и гонки с планировщиком, вложения, вопросы, отмену и восстановление после сбоя. HTTP smoke проверяет отдельный запрос и повтор отправки после перезапуска; `bun run test:attachments-runtime` проверяет его входные файлы, атрибуцию результата и отозванные полномочия через настоящий stdio/MCP без вызова модели. Браузерные сценарии различают заметку и запрос и проверяют увеличенные аватары на узких экранах в обеих темах.

Браузерные тесты используют порт 4318 и отдельную базу в `test-results/`. В CI запускаются те же проверки. Для уже установленного Chromium можно указать `PLAYWRIGHT_CHROMIUM_EXECUTABLE`.

Чтобы поставить задачи из чата агента в этом проекте, достаточно написать, например: **«Поставь Анне задачу проверить отчёт, а Ивану — исправить страницу входа»**. Агенту нужны доступ к запущенному brigd и возможность выполнять локальные команды. Инструкции в `AGENTS.md` и помощник `bun run brigd` позволяют ему самому найти сотрудников и создать назначенные карточки; вручную подключать MCP или задавать токен не нужно. Созданные карточки ждут ручного запуска.

Для клиентов без доступа к локальным командам есть **внешний MCP** по адресу `http://127.0.0.1:4310/mcp`. [Необязательная настройка внешнего подключения](docs/mcp.md).

Переменные окружения сервера (для каждого `BRIGD_*` поддерживается прежний `TRACKT_*`; новое имя имеет приоритет):

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `BRIGD_MODE` | `cli` | `cli` или `mock` |
| `BRIGD_DB` | `data/trackt.sqlite` или `data/demo.sqlite` | Файл SQLite относительно проекта либо абсолютный путь |
| `PORT` | `4310` | Порт сервиса; `dev` проксирует API на него. Разрешённые Host и Origin по умолчанию следуют за `PORT` |
| `BRIGD_HOST` | `127.0.0.1` | В контейнере `0.0.0.0`; нужны два явных allowlist ниже |
| `BRIGD_ALLOWED_HOSTS` | `127.0.0.1:4310,localhost:4310` | Разрешённые Host, через запятую, без wildcard |
| `BRIGD_ALLOWED_ORIGINS` | `http://127.0.0.1:4310,http://localhost:4310` | Точные Origin интерфейса, через запятую |
| `BRIGD_WORKSPACES_DIR` | `workspaces/` рядом с базой | Папки изолированных запусков и кандидатов слияния; ненужные папки и ветки запуска очищаются после переноса в целевую ветку или кнопкой **Очистить** в **Настройки → Хранилище** |
| `BRIGD_MAX_PARALLEL` | `4` | Общий лимит процессов агентов и проверки слияний, 1–32; сохранённое значение в **Настройки → Параллельность** имеет приоритет |
| `BRIGD_MAX_PER_REPOSITORY` | `1` | Лимит независимых агентов одного репозитория, 1–32; слияния всегда последовательные. Сохранённое значение в **Настройки → Параллельность** имеет приоритет |
| `BRIGD_INTEGRATION_CHECKS` | Не задано; реальные запуски заблокированы | JSON-массив команд проверки объединённого кода, без shell; сохранённое значение в **Настройки → Автопилот** имеет приоритет |
| `BRIGD_INTEGRATOR` | `auto` | `auto`: конфликт слияния сразу разрешает встроенный Интегратор; `manual`: только по кнопке в карточке |
| `BRIGD_DEFAULT_CWD` | Текущая папка сервиса | Начальное значение рабочей папки в форме; сохранённое значение в **Настройки → Общие** имеет приоритет |
| `BRIGD_CLI_HOME` | Домашняя папка пользователя сервиса | Где кнопки «Настроить разрешения…» раздела настроек «Разрешения» ищут и правят `~/.claude/settings.json` и `~/.codex/config.toml`; браузерные тесты направляют её в `test-results/` |
| `BRIGD_CLI_ACCESS` | `full` | Начальный режим обоих CLI: `full` без подтверждений и песочниц CLI или `standard` с ограничениями. Сохранённый выбор в **Настройки → Разрешения** имеет приоритет |
| `BRIGD_DEV` | `0` | `1` для dev-сервера; `bun run dev` задаёт автоматически |
| `BRIGD_MCP_TOKEN` | Не задано; внешний MCP отключён | Bearer-токен для `/mcp`, 32–256 символов `A–Z`, `a–z`, `0–9`, `_`, `-`; пустое значение отключает подключение. После изменения нужен перезапуск. [Подключение из IDE](docs/mcp.md) |

Переменные самого Compose (`TRACKT_MODE`, `TRACKT_UID`, `TRACKT_GID`, `TRACKT_PROJECTS_DIR`) сохраняют прежние имена; подробности в [инструкции контейнера](docs/container.md).

Структура: `src/` — Svelte UI, `server/store.ts` — данные/расписание, `server/engine.ts` — жизненный цикл, `server/adapter.ts` — CLI/mock, `server/protocol.ts` — валидация событий, `tests/` и `e2e/` — проверки.

## Проверенные границы

Локальные проверки ядра и сборки выполняются на Linux с Bun 1.4.2. Playwright-сценарии и Docker smoke включены в CI; статус конкретного коммита смотрите в GitHub Actions. CLI проверяются через `--help` без запросов к модели. Тесты CLI-протокола и процессов используют искусственные события/безвредные процессы. Авторизованные платные запросы к реальным моделям при разработке не выполнялись.

Основная целевая среда — Linux-контейнер. macOS и нативная Windows пока не заявлены как end-to-end проверенные. На Windows можно использовать Docker Desktop с Linux-контейнером; рабочая папка в карточке всегда задаётся путём внутри контейнера, например `/workspace/projects/my-project`.

MVP не устанавливает фоновую системную службу, не отправляет push-уведомления, не синхронизирует данные между устройствами и не восстанавливает автоматически результаты действий, выполненных вне brigd.
