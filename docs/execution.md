# Очередь запусков и слияние результатов

Ручные запуски, расписание, ответы на вопросы, повторы этапов и дополнительные запросы проходят через одну долговечную очередь SQLite. После перезапуска не начавшиеся запросы остаются в очереди. Для занятого расписания сохраняется один ожидающий запуск с последним наступившим интервалом, без накопления пропущенных запусков.

По умолчанию одновременно работают до четырёх процессов на разные репозитории и один агент на один репозиторий; лимиты меняются в **Настройки → Параллельность** (см. «Параллельная работа»). Проверка слияния занимает такой же процессный слот. Репозиторий определяется по каноническому пути общего Git-каталога: подпапки, симлинки и связанные worktree относятся к одной очереди. Разные независимые клоны имеют разные очереди.

## Изоляция изменений

Для новой реальной работы нужен Git-репозиторий с коммитом. Перед фактическим запуском brigd создаёт ветку `brigd/run-<ID>` и отдельный Git worktree от текущего сохранённого `HEAD`. Незакоммиченные изменения в исходной папке не копируются в запуск и не сбрасываются. Если задача задана для подпапки проекта, агент получает ту же подпапку в своём worktree.

Все этапы одного чек-листа используют один worktree. Ответ на вопрос и дополнительный запрос сохраняют прежнюю папку, ветку и точный ID CLI-сессии. Worktree, удалённый самим brigd после переноса результата или очисткой хранилища, создаётся заново из ветки `brigd/run-<ID>` при ответе, дополнительном запросе или новой проверке слияния; если ветка уже удалена, она восстанавливается из последнего перенесённого коммита (см. «Хранение рабочих папок»). Папка, пропавшая или заменённая без участия brigd, по-прежнему блокирует продолжение вместо создания новой под прежней сессией. Старые сессии, созданные до этой возможности, продолжаются в исходной папке; такая работа выполняется эксклюзивно и удерживает репозиторий при ожидании ответа.

## Параллельная работа

Лимиты задаются в **Настройки → Параллельность**:

- **Задач одновременно в одном репозитории** — сколько агентов одного репозитория работают сразу, каждый в своём worktree. По умолчанию 1: задачи репозитория идут по очереди. Запуск Интегратора и продолжения тоже занимают это место.
- **Всего процессов** — агенты всех репозиториев вместе с проверками слияния. По умолчанию 4. Если он меньше лимита репозитория, в одном репозитории одновременно работает не больше этого числа.

Допустимы целые значения 1–32. Сохранённое значение имеет приоритет над переменными `BRIGD_MAX_PER_REPOSITORY` и `BRIGD_MAX_PARALLEL`, сброс возвращает значение запуска сервиса. Изменение применяется к следующему запуску без перезапуска; при уменьшении лимита работающие процессы не останавливаются, новые ждут свободного места. Настройка хранится в базе и входит в бэкап. API: `GET/PATCH /api/settings/concurrency`; PATCH принимает `{ "maxPerRepository": 3, "maxParallel": 6 }` (любое из полей, `null` возвращает значение запуска), GET возвращает действующие `maxParallel` и `maxPerRepository`, сохранённые `saved` и значения запуска `defaults`. Через MCP — `get_concurrency_settings` и `update_concurrency_settings`.

Код параллельных задач разделён worktree, а в целевую ветку они попадают по правилам ниже, поэтому результаты не перезаписывают друг друга:

- Проверка и слияние результатов одного репозитория идут строго по одному. Следующий кандидат собирается от целевой ветки, в которую уже перенесён предыдущий результат, и проверяется вместе с ним.
- Готовый результат проверяется сразу, не дожидаясь остальных агентов репозитория: они продолжают работу в своих worktree, слияние их не затрагивает. Пока результат ждёт или проходит проверку, новые агенты этого репозитория не стартуют, чтобы начать уже с ним.
- Слияние ждёт работу, которую оно могло бы нарушить: агента в общей папке проекта (старые сессии), неподтверждённые прерванные процессы, продолжение в worktree этого же результата и Интегратора, который разрешает конфликт этого репозитория.
- Запуск Интегратора занимает первое свободное место репозитория раньше других ожидающих задач, а его результат проверяется раньше результатов, которые его ждали: целевая ветка не меняется под разрешённым конфликтом.

Семантические зависимости между задачами автоматически не определяются: зависимые изменения лучше объединить в последовательный чек-лист. Общие внешние сервисы и базы данных также не изолируются worktree. При лимите больше 1 тесты агентов и команды проверки слияния одного репозитория могут выполняться одновременно, поэтому они не должны занимать фиксированные порты, общие файлы вне рабочей папки или общую базу данных.

## Проверка и последовательное слияние

После успешного завершения всех этапов результат получает отдельный статус **Ожидает слияния**. Очередь слияний принимает результаты репозитория по одному; агенты в других worktree при этом продолжают работу (см. «Параллельная работа»). Во время проверки новые агенты этого репозитория ожидают в очереди.

1. Изменения исходного worktree сохраняются коммитом в его ветке. Служебные папки `.brigd-inputs-*` и `.brigd-outbox-*` исключаются из коммита; уже включённые в коммиты служебные файлы блокируют перенос.
2. От актуальной целевой ветки создаётся временный detached worktree. В нём объединяется результат агента с текущим кодом целевой ветки.
3. Запускаются команды проверки именно объединённого кода. При конфликте или ошибке целевая ветка не обновляется, а кандидат и результаты проверки остаются доступны в карточке до следующей попытки или очистки (см. «Хранение рабочих папок»).
4. Проверяется, что команды и Git hooks не изменили проверенный код, а исходный worktree остался прежним. Изменение целевой ветки во время проверки вызывает создание нового кандидата и повтор проверок; несколько последовательных изменений останавливают попытку до явного повтора.
5. Проверенный коммит переносится в целевую ветку. Если она открыта в рабочей папке, требуется чистое Git-состояние и применяется fast-forward. Если она нигде не открыта, ссылка обновляется с проверкой прежнего коммита. brigd не сбрасывает файлы, не прячет изменения в stash, не делает принудительное слияние и не отправляет коммиты в remote. Merge-коммиты, которые создаёт brigd (объединение целевой ветки в worktree задачи и проверенный коммит объединения), подписаны автором «Интегратор» (`integrator@localhost`), коммиттер берётся из настроек Git репозитория; коммит результата `brigd: результат <ID>` сохраняет обычную подпись, потому что это работа исполнителя задачи.

Целевая ветка запоминается при подготовке запуска. Работа из detached HEAD сохраняет результат, но автоматический перенос блокируется: нужна именованная целевая ветка. Если результат уже находится в целевой ветке, повтор не создаёт нового коммита. Дополнительный запрос может добавить изменения в ту же ветку worktree; они проходят новый цикл проверки и слияния.

Для Git-коммитов используется настроенная в репозитории личность; при её отсутствии — локальные параметры команды `brigd <brigd@localhost>`, без изменения Git-конфигурации. Hooks, подписи и доверие к репозиторию остаются действующими. Режим разрешений CLI выбирается в **Настройки → Разрешения**: полный доступ включён по умолчанию и отключает подтверждения и песочницы CLI; права ОС, границы контейнера и политики провайдеров сохраняются.

## Коммиты агента

В ограниченном режиме песочница Codex защищает `.git` от записи, поэтому команда `git commit` может завершиться ошибкой «Read-only file system». В полном доступе эта защита CLI отключена. Для коммита через brigd агент вызывает инструмент `commit_changes` в любом режиме. Коммит создаёт сам сервис в рабочей папке запуска: в ветке `brigd/run-<ID>` для worktree или в текущей ветке исходной папки для старых сессий. В коммит попадают новые, изменённые и удалённые файлы рабочей папки задачи или только перечисленные агентом пути. Изменения, проиндексированные вне этой области, и служебные папки не включаются. В сообщение добавляется строка `Brigd-Run: <ID>`.

Если в worktree идёт объединение с целевой веткой (например, его начал Интегратор), `commit_changes` создаёт merge-коммит всего worktree: Git не умеет частичные коммиты во время merge, поэтому `paths` отклоняются, а оставшиеся маркеры конфликта останавливают коммит с понятной ошибкой.

Git-каталог берётся из сохранённого снимка рабочей папки, а не из файла `.git`, который агент может переписать. Инструмент `commit_changes` не запускает Git hooks и fsmonitor: их код может находиться в папке, доступной агенту (например, `.husky`), и выполнился бы с правами сервиса. Эти ограничения инструмента сохраняются в обоих режимах; в полном доступе агент также может запускать Git напрямую. Результат worktree проходит проверку объединённого кода при слиянии; уже созданные агентом коммиты переносятся вместе с ним. Для старых сессий в исходной папке такой проверки нет. Инструмент коммитов не отправляет изменения в remote.

## Интегратор: регламент при конфликте слияния

Конфликт возникает, когда результат задачи и целевая ветка изменили одни и те же строки одного файла. Чаще всего это случается, если несколько агентов работают параллельно над одной областью кода или задача долго идёт до слияния. Чтобы конфликт не требовал ручной работы, в brigd есть встроенный работник **Интегратор**. Он не хранится в каталоге работников, его нельзя назначить задаче или архивировать; он показан отдельной карточкой в разделе **Работники**, где редактируется его единственный профиль.

Регламент по умолчанию (`BRIGD_INTEGRATOR=auto`):

1. Проверка слияния обнаруживает конфликт. Целевая ветка не меняется; конфликтующие файлы перечислены в карточке.
2. brigd сразу создаёт запуск Интегратора в той же задаче и том же worktree. Задача остаётся занята. Интегратор получает первое свободное место репозитория раньше других ожидающих задач; пока он работает, другие слияния этого репозитория ждут, чтобы целевая ветка не менялась под разрешаемым конфликтом.
3. Перед вызовом агента brigd сам выполняет `git merge --no-commit` актуальной целевой ветки в worktree задачи. Если к этому моменту конфликтов уже нет, агент не вызывается, а результат сразу отправляется на повторную проверку.
4. Интегратор получает перечень конфликтующих файлов, целевую ветку, команды проверки проекта, текст задачи и итог прежнего работника как контекст. Он правит файлы с маркерами так, чтобы сохранились и намерение задачи, и изменения целевой ветки, по возможности прогоняет проверки и завершает ход статусом `completed`. По инструкции Интегратор оставляет создание merge-коммита сервису. Его процесс получает текущий общий режим доступа CLI; в ограниченном режиме Codex также защищает `.git` песочницей.
5. brigd создаёт merge-коммит в ветке задачи (`brigd: объединение <ветка> в brigd/run-<ID>`) и запускает обычную проверку объединённого кода и перенос; этот результат проверяется первым среди ожидающих слияний репозитория. Если в файлах остались маркеры конфликта, слияние снова получает статус конфликта, а не ложный успех.

Провайдер, модель и уровень усилий Интегратора задаются в его профиле. По умолчанию (режим «как у запуска») они берутся у запуска, результат которого объединяется; режим «свои» фиксирует выбранный CLI для всех конфликтов независимо от исполнителя задачи. **Указания Интегратору** из профиля передаются агенту вместе с описанием конфликта как подчинённые недоверенные указания, например какие файлы не трогать или чью версию предпочитать; в карточках задач и истории они не показываются. Также передаются текущие включённые общие инструкции. Профиль фиксируется снимком при создании запуска, поэтому правки действуют со следующего конфликта. Сессия всегда новая. Запуск виден в истории как «Разрешение конфликта»; его сессию можно продолжить через **Отправить агенту**, например чтобы указать, какую версию оставить.

Если целевая ветка снова успела измениться и результат Интегратора тоже конфликтует, круг повторяется, но не больше трёх раз на один результат. После этого, а также в ручном режиме (`BRIGD_INTEGRATOR=manual`), конфликт остаётся в карточке с кнопкой **Поручить интегратору**. Если Интегратор завершился ошибкой или блокировкой, карточка показывает панель исходного слияния с теми же кнопками; новая попытка отменяет незавершённое объединение и начинает его заново от актуальной целевой ветки. Ошибки проверок после успешного объединения Интегратор не чинит: это по-прежнему статус «Проверка не прошла» для человека или дополнительного запроса.

Чтобы конфликтов было меньше: запускайте параллельные задачи только от зелёной целевой ветки (иначе каждый агент чинит сломанный тест по-своему), не давайте нескольким агентам одновременно одну область интерфейса или общий файл и предпочитайте короткие задачи, которые быстрее доходят до слияния.

## Автопилот: разбор очереди без участия человека

Автопилот — третий способ запуска после ручного и интервального. Задача с режимом **Автопилот** попадает в очередь раздела **Автопилот** и запускается, когда он включён, подошла её очередь и есть свободные слот и репозиторий. Проверки те же, что для любого запуска: лимит процессов, лимит агентов на репозиторий, занятость репозитория проверкой слияния и неподтверждённые прерванные запуски; дополнительно автопилот не берёт задачу, если в репозитории уже есть ожидающий запрос очереди. Запуск создаётся только в момент старта с триггером `autopilot`; до этого задача остаётся обычной редактируемой карточкой, а выключение автопилота ничего не отменяет.

Очередь сначала упорядочена по приоритету задачи (`tasks.priority`: `critical`, `high`, `normal`, `low`; по умолчанию `normal`), а внутри одного приоритета — так, как её расставил человек: новая задача или задача, переключённая в режим **Автопилот**, встаёт в конец своего приоритета, а перетаскивание в разделе **Автопилот** (или стрелки ↑ и ↓ на значке перемещения) ставит задачу перед другой задачей того же приоритета. Место хранится в `tasks.autopilot_position`; отложенная задача его сохраняет, смена режима запуска его сбрасывает, смена приоритета переносит задачу в конец нового приоритета, а восстановленная из архива задача встаёт в конец своего приоритета. Задачи, сохранённые до появления приоритета, при открытии базы получают `normal`. Если репозиторий более срочной задачи занят, автопилот не простаивает и берёт задачу другого репозитория; менее срочная задача того же репозитория при этом тоже ждёт. Задачи, сохранённые до появления порядка, при открытии базы встают в конец по дате создания. Задача занятого репозитория пропускается, пока он занят, задачи других репозиториев её не ждут; при лимите 1 задача на репозиторий следующая задача стартует от целевой ветки уже с результатом предыдущей, если его слияние прошло; при большем лимите автопилот занимает свободные места репозитория параллельно. Задача берётся один раз за сессию: статусы «Ошибка», «Заблокировано» и «Нужен ответ» ждут человека. Три запуска подряд со статусом ошибки или блокировки выключают автопилот (причина сохраняется и показывается в разделе, в карточке последней задачи появляется системный комментарий); результат или вопрос агента сбрасывают счётчик, отмена не учитывается. Время остановки прекращает только взятие новых задач. Перезапуск сервиса выключает автопилот так же, как не возобновляет прерванные запуски. Недоступная рабочая папка фиксируется как заблокированная попытка и учитывается предохранителем. Исчерпание лимитов CLI обрабатывается до предохранителя: если в **Настройки → Общие** или в профиле работника выбрана замена, ход передаётся ей в новой сессии и не считается ошибкой (см. README, раздел про общие настройки).

Состояние хранится в SQLite (таблица `autopilot`, одна строка) и доступно через `GET/PATCH /api/autopilot`: `enabled`, `until`, `startedAt`, `stoppedAt`, `stopReason` (`manual`, `until`, `failures`, `restart`), `failures`, а также `pool` (очередь в порядке взятия) и `attempts` (запуски текущей или последней сессии). `POST /api/tasks/:id/queue` с телом `{"beforeTaskId": "…"}` ставит задачу перед указанной задачей того же приоритета (задача другого приоритета отклоняется с `409`), с `null` — в конец её приоритета, и возвращает тот же обзор; приоритет задаётся полем `priority` в `POST /api/tasks` и `PATCH /api/tasks/:id`; через MCP то же делает `move_autopilot_task`. Раздел **Итоги сессии** не показывает задачи, перенесённые в архив. Mock-режим поддерживает автопилот без Git-worktree. Проверки — в `tests/store.test.ts`, `tests/engine.test.ts`, `tests/execution-queue.test.ts` и браузерном сценарии `e2e/autopilot.spec.ts`. Подготовка CLI к работе без подтверждений описана в [cli-permissions.md](cli-permissions.md).

## Команды проверки

Перед реальным запуском откройте **Настройки → Автопилот** и сохраните значение **BRIGD_INTEGRATION_CHECKS**: JSON-массив команд, каждая команда — массив аргументов. Например:

```json
[["bun","install","--frozen-lockfile"],["bun","run","verify"]]
```

Значение сохраняется в SQLite и применяется без перезапуска сервиса. Оно имеет приоритет над одноимённой переменной окружения. Переменную можно использовать как исходную настройку сервиса:

```sh
BRIGD_INTEGRATION_CHECKS='[["bun","install","--frozen-lockfile"],["bun","run","verify"]]' bun run start
```

Команды запускаются в корне объединённого кандидата без оболочки. Допускается от 1 до 10 команд. Для других стеков задайте собственные команды, например `[["python","-m","pytest"]]`. Наличие зависимостей и сетевого доступа определяется окружением сервиса.

Без явно заданных команд реальные ручные, интервальные запуски и автопилот заблокированы; продолжение, повтор, дополнительный запрос, запуск Интегратора и проверка слияния также требуют этой настройки. Отсутствие настройки не создаёт запуск и не расходует срок интервальной задачи. Mock-режим работает без команд проверки.

Чтобы исправить команды для уже сохранённой работы, сохраните новое значение в **Настройки → Автопилот** и нажмите **Повторить проверку и слияние**. Очистить сохранённое значение, если это оставит сервис без команд, нельзя при включённом автопилоте или незавершённой работе.

API настройки: `GET/PATCH /api/settings/autopilot`. PATCH принимает `{ "integrationChecks": [["python", "-m", "pytest"]] }`; `{ "integrationChecks": null }` удаляет сохранённое значение и возвращает сервис к переменной окружения. GET возвращает `integrationChecks` и `source` (`settings`, `environment` или `null`).

## Ошибки, отмена и восстановление

Карточка показывает отдельные состояния слияния, ошибки, коды завершения проверок, конфликтующие файлы, коммит результата и папку кандидата, пока кандидат не удалён после переноса, повторной попытки или очистки хранилища. Конфликт по умолчанию разрешает Интегратор (см. выше). Вручную его можно разрешить в исходном worktree: выполните там `git merge <целевая ветка>`, исправьте файлы и, не делая коммит, нажмите **Повторить проверку и слияние**: brigd сам создаст merge-коммит, если маркеров конфликта не осталось. Можно и отправить дополнительный запрос агенту задачи. После сохранения пользовательских файлов целевой ветки либо исправления причин ошибки можно повторить проверку.

Отмена проверки удерживает слот репозитория до завершения процессов, включая дочерние процессы команд. Уже выполненные Git-операции не откатываются. После сбоя сервиса активная работа и проверка помечаются прерванными; их резервирование сохраняется. Перед продолжением или отменой требуется подтвердить, что прежние процессы остановлены. Это подтверждение относится к восстановлению очереди и не предоставляет нативных разрешений CLI или файловой системе.

Длительность агента и проверки не ограничена десятью минутами: выполнение заканчивается результатом, ошибкой или отменой. Короткие таймауты диагностики CLI и подготовки worktree остаются отдельными техническими проверками.

## Хранение рабочих папок

Каталог worktree и кандидатов по умолчанию находится рядом с базой, в `data/workspaces/`; можно указать `BRIGD_WORKSPACES_DIR`. Папки занимают место (после проверок в кандидате лежат `node_modules` и сборка), поэтому действует политика хранения:

- После успешного переноса результата в целевую ветку brigd удаляет больше не нужные worktree запуска и кандидат проверки, ещё до того как слияние получит статус **Изменения перенесены**. Общий worktree сохраняется, пока нужен другому активному или прерванному запуску; папки с репозиториями подмодулей также сохраняются. После удаления worktree удаляется и ветка `brigd/run-<ID>`, если её вершина совпадает с сохранённым последним перенесённым коммитом (`lastIntegratedCommit`), этот коммит по-прежнему входит в историю записанной целевой ветки, а сама ветка запуска нигде не открыта в worktree. Изменённая после переноса ветка сохраняется. Работа остаётся в истории целевой ветки, удаляется только ссылка ветки запуска. В логах задачи появляется запись «Рабочая папка запуска удалена после слияния» с освобождённым объёмом; в истории запуска у снимка рабочей папки показана дата удаления. Незакоммиченные файлы worktree к этому моменту невозможны (слияние требует чистого worktree), а служебные папки `.brigd-inputs-*` и `.brigd-outbox-*` удаляются вместе с ним — результаты, которые нужно сохранить, агент публикует как вложения.
- Папки активных, прерванных, конфликтных, завершившихся ошибкой или блокировкой и ещё не перенесённых запусков сохраняются: они нужны для продолжения точных сессий, повтора, разбора конфликта и повторной проверки. Worktree и кандидаты с репозиториями подмодулей Git тоже сохраняются: их коммиты могут храниться только в служебной папке worktree. Кандидат остаётся при конфликте, ошибке проверок, блокировке и прерывании; при повторной попытке прежний кандидат удаляется, при отмене или перестроении из-за изменившейся целевой ветки — тоже. После успешного переноса продолжения или результата Интегратора удаляются и кандидаты прежних завершённых попыток в той же рабочей папке: уже разрешённый конфликт не удерживает их бессрочно. Кандидаты активных и прерванных попыток сохраняются.
- Ответ на вопрос, дополнительный запрос или новая проверка слияния для запуска, папка которого была удалена, создают worktree заново по тому же пути из ветки `brigd/run-<ID>`; если ветка удалена, brigd восстанавливает её из последнего перенесённого коммита. Сохранённый ID CLI-сессии и путь не меняются. Неотслеживаемые файлы прежней сессии не восстанавливаются. Папка, пропавшая без участия brigd, по-прежнему блокирует продолжение вместо создания новой.
- **Настройки → Хранилище** показывает занятое место по каталогу: сколько можно освободить и сколько ещё нужно, с папками по причинам (активный запуск, прерван, конфликт, ошибка, ещё не перенесён) и подсказкой, что сделать с каждой группой. Кнопка **Очистить** после подтверждения удаляет папки отменённых запусков и уже перенесённых результатов, устаревшие кандидаты и worktree запусков без записи в базе (например, оставшиеся после восстановления другого бэкапа); галочка в подтверждении добавляет кандидаты неудачных проверок и заблокированных переносов. Очистка также удаляет ветки уже перенесённых результатов по тем же проверкам, что и после слияния, в том числе если папка была удалена раньше. Такие ветки перечислены отдельно; кнопку можно использовать и без папок. Ветки отменённых или неизвестных запусков с неподтверждённым переносом сохраняются. Удаляются только обычные папки внутри служебных подпапок каталога: сохранённый путь должен соответствовать записи brigd, а для worktree без записи принадлежность подтверждается Git-данными известного репозитория; файлы, символические ссылки, посторонние папки и worktree, чей путь в базе отличается от каталога (после переноса базы или смены `BRIGD_WORKSPACES_DIR`), только показываются. Если каталог совпадает с корнем, домашней папкой или содержит базу brigd, раздел сообщает об этом и ничего не трогает. Во время очистки очередь не берёт новую работу, одновременно выполняется одна очистка; решение по каждой папке и ветке перепроверяется непосредственно перед удалением. API: `GET /api/settings/storage` возвращает `available`, `note`, `root`, `totalBytes`, `reclaimableBytes`, `retainedBytes`, список имён удаляемых веток `reclaimableBranches` и `entries` с `kind` (`worktree`, `candidate`, `unknown`), `retained`, `optional` и `reason`; `POST /api/settings/storage/cleanup` с `{}` или `{ "includeCandidates": true }` возвращает количество удалённых папок `removed`, количество удалённых веток `removedBranches`, `freedBytes`, `failures` и обновлённый обзор. В mock-режиме `available: false`.

Резервная копия для возобновления сессий должна сохранять базу, рабочие папки, исходный репозиторий и его общие Git-данные. Публикация в remote не выполняется.

Mock-режим использует очередь, но не создаёт Git-worktree и не переносит код. Демо-запуски не меняют файлы, поэтому подчиняются лимиту задач в одном репозитории так же, как запуски в worktree. Проверки очереди и слияний в `tests/execution-queue.test.ts` и `tests/integration.test.ts` используют настоящие временные Git-репозитории и управляемые тестовые агенты без запросов к моделям.
