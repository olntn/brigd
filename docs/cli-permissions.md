# Разрешения CLI для работы без присмотра

Ночью некому нажать «Разрешить». Эта инструкция описывает, что настроить в Claude Code и Codex, чтобы запуски brigd, в том числе из очереди [автопилота](../README.md#автопилот), не заканчивались статусом **Заблокировано**. brigd сам не меняет режим разрешений CLI и не добавляет флаги обхода: всё, что описано ниже, вы настраиваете в самих CLI.

В приложении эти шаги делают кнопки в настройках, раздел **Разрешения**; кнопка **Инструкция** там же показывает этот текст. «Настроить разрешения Claude Code» дописывает недостающие allow-правила в `~/.claude/settings.json` пользователя, от которого запущен сервис; остальные ключи сохраняются, прежний файл копируется в `settings.json.bak`, непонятный файл не перезаписывается. «Настроить разрешения Codex» дописывает в `~/.codex/config.toml` те же параметры, что brigd передаёт флагами: `sandbox_mode = "workspace-write"`, `approval_policy = "on-request"` и `network_access = true` в таблице `sandbox_workspace_write`; остальные ключи и комментарии сохраняются, прежний файл копируется в `config.toml.bak`. Состояние «Разрешения включены» у обоих CLI означает одно и то же: нужные параметры есть в файле. Ниже описано, что именно они делают и как сделать то же вручную.

## Что фиксирует brigd

При каждом запуске brigd передаёт CLI свои аргументы, и они имеют приоритет над вашими конфигами:

| CLI | Аргументы brigd | Что это значит |
|---|---|---|
| Claude Code | `claude -p --permission-mode default`; `--allowedTools` только для собственных MCP-инструментов brigd | В режиме печати CLI не может задать вопрос: правка файла или команда без allow-правила отклоняется, brigd видит отказ и завершает запуск блокировкой |
| Codex | `codex exec --sandbox workspace-write -c approval_policy="on-request"`, сеть внутри песочницы включена | Внутри рабочей папки Codex правит файлы и запускает команды без вопросов; действия вне папки отклоняются, одобрить их некому |

Поэтому для Codex настраивать нечего, а для Claude Code нужны allow-правила. Значение `permissions.defaultMode` в настройках Claude Code не поможет: флаг `--permission-mode` на командной строке сильнее. Ответ в карточке brigd тоже не является разрешением: карточка принимает уточнения по задаче, а не системные подтверждения CLI.

## Claude Code

### Где хранятся правила

Claude Code читает правила из нескольких файлов. Для запусков brigd важно, какие из них видны внутри рабочей папки запуска: новые запуски идут в отдельном Git worktree, который создаётся из коммита.

| Файл | Область | Виден в запусках brigd |
|---|---|---|
| `~/.claude/settings.json` | Пользователь, все проекты | Да. Это домашняя папка того пользователя Linux, от которого запущен brigd и выполнен вход в CLI. В контейнере это том `trackt-cli-home` |
| `.claude/settings.json` в репозитории проекта | Проект, файл коммитится | Да, если файл закоммичен |
| `.claude/settings.local.json` | Проект, файл не коммитится | Git не переносит файл в worktree; для запусков brigd используйте пользовательские настройки |

Если brigd правит собственный репозиторий, используйте пользовательский файл: папка `.claude/` в нём добавлена в `.gitignore`.

### Какие правила нужны

Базовый набор для проекта на Bun. Кнопка **Настройки → Разрешения → Настроить разрешения Claude Code** добавляет эти allow-правила. Они покрывают только перечисленные команды: например, `bun run build`, `npm test` и инструмент `WebFetch` потребуют отдельных правил. Остальные ключи файла, например `model` или `theme`, оставьте как есть и добавьте только блок `permissions`:

```json
{
  "permissions": {
    "allow": [
      "Edit",
      "Write",
      "Bash(bun install:*)",
      "Bash(bun test:*)",
      "Bash(bun run check:*)",
      "Bash(bun run verify:*)",
      "Bash(git status:*)",
      "Bash(git diff:*)",
      "Bash(git log:*)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)"
    ]
  }
}
```

- `Edit` и `Write` разрешают правки файлов. Чтобы ограничить область, укажите путь относительно корня проекта: `Edit(src/**)`, `Write(docs/**)`.
- `Bash(bun test:*)` разрешает команды, начинающиеся с `bun test`. Перечисляйте только проверенные команды проекта. `bun install` нужен потому, что worktree запуска создаётся без `node_modules`.
- Для других стеков замените команды, например `Bash(python -m pytest:*)` или `Bash(make test:*)`.
- `deny` и `ask` сильнее `allow`: запрет или запрос подтверждения остаётся в силе даже при наличии разрешающего правила. В `deny` удобно добавить файлы с секретами и запрещённые команды; `ask` потребует интерактивного подтверждения.

Правила читаются при каждом старте процесса CLI: текущие процессы продолжают работать по старым, новые запуски и продолжения сессий получают новые. В контейнере файл правится внутри него: `docker compose exec trackt sh -c 'mkdir -p ~/.claude && ${EDITOR:-vi} ~/.claude/settings.json'`.

### Через интерфейс Claude Code

Вместо редактирования файла откройте `claude` в папке проекта, введите `/permissions` и добавьте те же правила. Для запусков brigd выбирайте пользовательскую область сохранения (`~/.claude/settings.json`).

### Проверка

1. Создайте в brigd ручную задачу для работника с Claude Code: «Добавь комментарий в начало файла README.md и запусти bun test».
2. Дождитесь завершения. Статус **Завершено** означает, что правил достаточно для этой задачи. Строка «Применяются штатные правила разрешений CLI» описывает режим запуска, но не гарантирует разрешение всех действий.
3. При статусе **Заблокировано** с текстом про native permission approval сначала откройте **Настройки → Разрешения → Настроить разрешения Claude Code**. Кнопка добавляет базовые правила, но не снимает все возможные запреты.
4. Если базовые правила уже есть, посмотрите отклонённый инструмент и безопасные метаданные операции в сообщении блокировки или логах. Точную команду и контекст проверьте в сохранённой Claude-сессии: папки запусков лежат в `data/workspaces/` рядом с базой, выполните в рабочей папке запуска `claude --resume <ID сессии>`; ID показан в истории запусков карточки.
5. Если действие допустимо, добавьте узкое правило через `/permissions` или `~/.claude/settings.json`, учитывая существующие `deny`- и `ask`-правила. Затем для обычной заблокированной задачи отправьте дополнительный запрос **«Продолжи задачу»**, а для отдельного этапа повторите этот этап. Дополнительный запрос возобновляет работу после настройки правил и сам по себе не выдаёт разрешение CLI.

Не вводите в карточку brigd пароли и не пытайтесь «разрешить» действие комментарием: это не работает по замыслу.

## Codex

### Что уже сделано за вас

brigd запускает `codex exec` с песочницей `workspace-write`, политикой подтверждений `on-request` и включённой сетью. Внутри рабочей папки это даёт правки файлов, тесты, локальные серверы и установку пакетов без единого вопроса. Настройки `sandbox_mode` и `approval_policy` из `~/.codex/config.toml` на запуски brigd не влияют: аргументы командной строки сильнее. Кнопка в настройках дописывает в файл те же три параметра, чтобы интерактивный `codex` в тех же папках вёл себя одинаково с запусками brigd; вручную это выглядит так:

```toml
sandbox_mode = "workspace-write"
approval_policy = "on-request"

[sandbox_workspace_write]
network_access = true
```

Автоматически отклоняются и настройками не чинятся: запись вне рабочей папки и действия, для которых Codex запрашивает эскалацию. Если задача требует такого, вынесите действие в команды проверки brigd или выполните его вручную.

### Что проверить

1. Вход: `codex login` в терминале того же пользователя Linux. В контейнере: `docker compose exec trackt codex login --device-auth`, подробности в [container.md](container.md#codex).
2. Git: Codex требует Git-репозиторий; worktree brigd ему удовлетворяет.
3. Доверие к папке запрашивает только интерактивный `codex`; `codex exec` в brigd не спрашивает. Если хотите открывать те же папки интерактивно, подтвердите доверие один раз.
4. Проверка такая же, как для Claude Code: ручная задача с правкой файла и запуском тестов.

## Остальная подготовка к ночи

- **Целевая ветка.** В папке проекта выполните `git status --short`: вывод должен быть пустым. Незавершённое закоммитьте или спрячьте в `git stash`, переключитесь на ветку, в которую должны попадать результаты. Перенос делается fast-forward и требует чистого состояния.
- **Команды проверки.** В **Настройки → Автопилот** сохраните значение **BRIGD_INTEGRATION_CHECKS**, например:

  ```json
  [["python","-m","pytest"]]
  ```

  Настройка одна на весь сервис, применяется без перезапуска и имеет приоритет над переменной окружения `BRIGD_INTEGRATION_CHECKS`. Без неё реальные запуски, продолжения и проверка слияния заблокированы. Можно также задать переменную в файле `.env` рядом с brigd; Bun читает его при запуске. Подробности в [execution.md](execution.md#команды-проверки).
- **Компьютер и сервер.** Планировщик работает, пока запущен `bun run start`. Отключите сон компьютера; в WSL2 сон Windows останавливает и brigd. Терминал удобно держать в `tmux`.
- **Автопилот.** Включите его на вкладке **Автопилот** с временем остановки. Правила сессии и предохранитель описаны в [README](../README.md#автопилот).
