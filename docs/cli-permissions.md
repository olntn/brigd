# Разрешения CLI для работы без присмотра

В **Настройки → Разрешения** есть общий переключатель **Полный доступ Codex и Claude Code**. По умолчанию он включён: оба CLI выполняют команды и записывают файлы без своих подтверждений и песочниц, с правами пользователя, от которого запущен brigd. Права ОС, границы контейнера, вход в аккаунты, лимиты и политики провайдеров сохраняются.

Режим сохраняется в базе и применяется без перезапуска сервиса к новым процессам CLI: обычным задачам, этапам, автопилоту, Интегратору и продолжениям сохранённых сессий. Уже запущенные процессы сохраняют прежний режим. После изменения режима повторите заблокированный этап или отправьте обычной заблокированной задаче дополнительный запрос **«Продолжи задачу»**, чтобы brigd запустил новый процесс.

API: `GET/PATCH /api/settings/permissions`, значение `{"mode":"full"}` для полного доступа или `{"mode":"standard"}` для ограниченного режима. Настройка относится к CLI, запускаемым brigd; пользовательские файлы CLI она не изменяет.

Если сохранённого выбора ещё нет, начальный режим задаёт `BRIGD_CLI_ACCESS=full|standard` (прежнее имя `TRACKT_CLI_ACCESS` тоже поддерживается). Без переменной используется `full`. Сохранённый в интерфейсе режим имеет приоритет над переменной окружения.

## Что фиксирует brigd

При каждом запуске brigd передаёт CLI свои аргументы, и они имеют приоритет над вашими конфигами:

| Режим и CLI | Аргументы brigd | Что это значит |
|---|---|---|
| Полный доступ, Claude Code | `claude -p --dangerously-skip-permissions --settings '{"sandbox":{"enabled":false}}'` | Подтверждения инструментов и песочница Claude Code отключены |
| Полный доступ, Codex | `codex exec --dangerously-bypass-approvals-and-sandbox` | Подтверждения инструментов и песочница Codex отключены |
| Ограниченный, Claude Code | `claude -p --permission-mode default`; `--allowedTools` только для собственных MCP-инструментов brigd | Правка файла или команда без allow-правила отклоняется; интерактивного подтверждения в brigd нет |
| Ограниченный, Codex | `codex exec --sandbox workspace-write -c approval_policy="on-request"`, сеть внутри песочницы включена | В рабочей папке разрешены правки и команды; запись вне папки или запрос эскалации блокируется |

В полном доступе кнопки настройки файлов CLI не нужны. Чтобы вернуть ограничения, выключите переключатель. Тогда появится раздел **Настройки ограниченного режима** с путями к конфигам и кнопками **Настроить разрешения…**. Кнопка **Инструкция** доступна в обоих режимах.

В ограниченном режиме «Настроить разрешения Claude Code» дописывает недостающие allow-правила в `~/.claude/settings.json` пользователя сервиса; остальные ключи сохраняются, прежний файл копируется в `settings.json.bak`, непонятный файл не перезаписывается. «Настроить разрешения Codex» дописывает в `~/.codex/config.toml` параметры `workspace-write`, `on-request` и сеть внутри песочницы; остальные ключи и комментарии сохраняются, прежний файл копируется в `config.toml.bak`. Состояние **Разрешения включены** означает наличие этих параметров в файле, а не полный доступ.

Далее описана настройка ограниченного режима. Ответ в карточке brigd принимает уточнения по задаче и не выдаёт системное разрешение CLI. Значение `permissions.defaultMode` в настройках Claude Code не заменяет переключатель: аргументы запуска brigd сильнее.

## Claude Code в ограниченном режиме

### Где хранятся правила

Claude Code читает правила из нескольких файлов. Для запусков brigd важно, какие из них видны внутри рабочей папки запуска: новые запуски идут в отдельном Git worktree, который создаётся из коммита.

| Файл | Область | Виден в запусках brigd |
|---|---|---|
| `~/.claude/settings.json` | Пользователь, все проекты | Да. Это домашняя папка того пользователя Linux, от которого запущен brigd и выполнен вход в CLI. В контейнере это том `trackt-cli-home` |
| `.claude/settings.json` в репозитории проекта | Проект, файл коммитится | Да, если файл закоммичен |
| `.claude/settings.local.json` | Проект, файл не коммитится | Git не переносит файл в worktree; для запусков brigd используйте пользовательские настройки |

Если brigd правит собственный репозиторий, используйте пользовательский файл: папка `.claude/` в нём добавлена в `.gitignore`.

### Какие правила нужны

Базовый набор для проекта на Bun. Кнопка **Настройки → Разрешения → Настроить разрешения Claude Code** в ограниченном режиме добавляет эти allow-правила. Они покрывают только перечисленные команды: например, `bun run build`, `npm test` и инструмент `WebFetch` потребуют отдельных правил. Составная Bash-команда может требовать правил для каждой операции, поэтому разрешённый `ls` не разрешает следующий `head` или `python3`. Остальные ключи файла, например `model` или `theme`, оставьте как есть и добавьте только блок `permissions`:

```json
{
  "permissions": {
    "allow": [
      "Edit",
      "Write",
      "Bash(bun install:*)",
      "Bash(bun test:*)",
      "Bash(bun run check:*)",
      "Bash(bun run verify:*)",
      "Bash(git status:*)",
      "Bash(git diff:*)",
      "Bash(git log:*)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)"
    ]
  }
}
```

- `Edit` и `Write` разрешают правки файлов. Чтобы ограничить область, укажите путь относительно корня проекта: `Edit(src/**)`, `Write(docs/**)`.
- `Bash(bun test:*)` разрешает команды, начинающиеся с `bun test`. Перечисляйте только проверенные команды проекта. `bun install` нужен потому, что worktree запуска создаётся без `node_modules`, в том числе когда папка создаётся заново после удаления при слиянии или очистке хранилища.
- Для других стеков замените команды, например `Bash(python -m pytest:*)` или `Bash(make test:*)`.
- `deny` и `ask` сильнее `allow`: запрет или запрос подтверждения остаётся в силе даже при наличии разрешающего правила. В `deny` удобно добавить файлы с секретами и запрещённые команды; `ask` потребует интерактивного подтверждения.

Правила читаются при каждом старте процесса CLI: текущие процессы продолжают работать по старым, новые запуски и продолжения сессий получают новые. В контейнере файл правится внутри него: `docker compose exec trackt sh -c 'mkdir -p ~/.claude && ${EDITOR:-vi} ~/.claude/settings.json'`.

### Через интерфейс Claude Code

Вместо редактирования файла откройте `claude` в папке проекта, введите `/permissions` и добавьте те же правила. Для запусков brigd выбирайте пользовательскую область сохранения (`~/.claude/settings.json`).

### Проверка

1. Создайте в brigd ручную задачу для работника с Claude Code: «Добавь комментарий в начало файла README.md и запусти bun test».
2. Дождитесь завершения. Статус **Завершено** означает, что правил достаточно для этой задачи. Строка «Применяются штатные правила разрешений CLI» описывает режим запуска, но не гарантирует разрешение всех действий.
3. При статусе **Заблокировано** с текстом про native permission approval сначала откройте **Настройки → Разрешения → Настроить разрешения Claude Code**. Кнопка добавляет базовые правила, но не снимает все возможные запреты.
4. Если базовые правила уже есть, откройте запись ошибки инструмента во вкладке **Логи** и скопируйте блок **Ошибка**. В нём видны причина отказа и операции, которым требуется разрешение. Контекст также можно открыть в сохранённой Claude-сессии: папки запусков лежат в `data/workspaces/` рядом с базой, выполните в рабочей папке запуска `claude --resume <ID сессии>`; ID показан в истории запусков карточки.
5. Если действие допустимо, добавьте узкое правило через `/permissions` или `~/.claude/settings.json`, учитывая существующие `deny`- и `ask`-правила. Затем для обычной заблокированной задачи отправьте дополнительный запрос **«Продолжи задачу»**, а для отдельного этапа повторите этот этап. Дополнительный запрос возобновляет работу после настройки правил и сам по себе не выдаёт разрешение CLI.

Не вводите в карточку brigd пароли и не пытайтесь «разрешить» действие комментарием: это не работает по замыслу.

## Codex в ограниченном режиме

### Что уже сделано за вас

В ограниченном режиме brigd запускает `codex exec` с песочницей `workspace-write`, политикой подтверждений `on-request` и включённой сетью. В рабочей папке доступны правки файлов, тесты, локальные серверы и установка пакетов; метаданные `.git` защищены песочницей. Настройки `sandbox_mode` и `approval_policy` из `~/.codex/config.toml` на запуски brigd не влияют: аргументы командной строки сильнее. Кнопка в настройках дописывает в файл те же три параметра для интерактивного `codex`; вручную это выглядит так:

```toml
sandbox_mode = "workspace-write"
approval_policy = "on-request"

[sandbox_workspace_write]
network_access = true
```

В ограниченном режиме автоматически отклоняются запись вне рабочей папки и действия, для которых Codex запрашивает эскалацию. Для таких задач включите **Полный доступ Codex и Claude Code** либо выполните действие вручную.

### Что проверить

1. Вход: `codex login` в терминале того же пользователя Linux. В контейнере: `docker compose exec trackt codex login --device-auth`, подробности в [container.md](container.md#codex).
2. Git: Codex требует Git-репозиторий; worktree brigd ему удовлетворяет.
3. Доверие к папке запрашивает только интерактивный `codex`; `codex exec` в brigd не спрашивает. Если хотите открывать те же папки интерактивно, подтвердите доверие один раз.
4. Проверка такая же, как для Claude Code: ручная задача с правкой файла и запуском тестов.

## Остальная подготовка к ночи

- **Целевая ветка.** В папке проекта выполните `git status --short`: вывод должен быть пустым. Незавершённое закоммитьте или спрячьте в `git stash`, переключитесь на ветку, в которую должны попадать результаты. Перенос делается fast-forward и требует чистого состояния.
- **Команды проверки.** В **Настройки → Автопилот** сохраните значение **BRIGD_INTEGRATION_CHECKS**, например:

  ```json
  [["python","-m","pytest"]]
  ```

  Настройка одна на весь сервис, применяется без перезапуска и имеет приоритет над переменной окружения `BRIGD_INTEGRATION_CHECKS`. Без неё реальные запуски, продолжения и проверка слияния заблокированы. Можно также задать переменную в файле `.env` рядом с brigd; Bun читает его при запуске. Подробности в [execution.md](execution.md#команды-проверки).
- **Компьютер и сервер.** Планировщик работает, пока запущен `bun run start`. Отключите сон компьютера; в WSL2 сон Windows останавливает и brigd. Терминал удобно держать в `tmux`.
- **Автопилот.** Включите его на вкладке **Автопилот** с временем остановки. Правила сессии и предохранитель описаны в [README](../README.md#автопилот).
