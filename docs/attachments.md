# Файлы, изображения и инструменты агента

К задаче, комментарию и ответу на уточнение можно прикреплять файлы. Например, пользователь добавляет скриншот с просьбой исправить интерфейс, а агент возвращает скриншоты результата и отчёт в этой же задаче.

## В интерфейсе

- Выберите файлы, перетащите их в область вложений или вставьте изображение из буфера обмена.
- В редакторе задачи файлы сохраняются вместе с задачей. В комментарии и ответе агенту они отправляются вместе с текстом.
- До сохранения файлы находятся во временной загрузке. Ошибка отправки не должна заставлять загружать уже принятые файлы заново.
- Проверенные растровые изображения получают уменьшенное превью. Нажатие на превью открывает изображение в окне на весь экран с изменением масштаба: колесо мыши, жест двумя пальцами, перетаскивание, кнопки масштаба и клавиши `+`, `-`, `0` (вписать) и `1` (100 %). Полноразмерный просмотр и кнопка «Открыть в новом окне» показывают перекодированную копию изображения без метаданных; оригинальные байты возвращает только кнопка скачивания.
- HTML, SVG и неизвестные форматы доступны для скачивания без исполнения в интерфейсе. Неподдерживаемое или повреждённое изображение может остаться файлом без превью.
- Обычный комментарий и загрузка файла сами по себе не запускают агента. Чтобы продолжить ожидающую сессию, отправьте ответ через панель уточнения.

## Какие файлы видит запуск

Новый запуск получает зафиксированный список вложений задачи и её комментариев. Позднее изменение задачи не переписывает входные данные уже начавшегося запуска.

Ответ на уточнение добавляет выбранные файлы к следующему ходу той же сессии. В сложной задаче следующий работник получает прежние входные данные и опубликованные результаты предыдущих этапов. При повторе этапа сохраняются предыдущие входные файлы и результаты этого запуска. Не связанные с ответом поздние загрузки не подмешиваются в работающий ход.

Привязки к запуску, этапу и попытке сохраняются рядом с автором файла. Удаление файла из редактируемого списка задачи не меняет старые снимки запуска.

## MCP для Codex и Claude Code

brigd запускает небольшой MCP-помощник через stdio на время каждого вызова CLI. Для этих агентов отдельный публичный MCP-сервер, постоянный токен и изменение пользовательского файла конфигурации не нужны. Для независимого подключения из IDE есть [внешний MCP через Streamable HTTP](mcp.md), который включается переменной `BRIGD_MCP_TOKEN`.

Помощник запускается из сборки `dist/task-mcp-stdio.js`, только если она не старше исходников `server/*.ts` и `src/lib/*.ts`. Иначе brigd берёт `server/task-mcp-stdio.ts`. Так `bun run dev`, который не пересобирает `dist`, после обновления сразу выдаёт агентам новые инструменты, например `set_progress`: устаревшая сборка их бы скрыла, хотя протокол задачи уже просит их вызывать.

Помощник читает задачи по ID и управляет приложением через его штатные проверки. Инструменты чтения и публикации результатов:

- `get_task`: название, описание, статус задачи и первая страница метаданных её вложений
- `list_comments`: история обсуждения выбранной задачи, от старых сообщений к новым; текст, тип сообщения (`kind`), запуск, этап и метаданные вложений
- `list_attachments`: список доступных вложений
- `read_attachment`: чтение до 16 КиБ исходного файла за вызов; `materialize=true` создаёт локальную копию оригинала для нативных файловых инструментов
- `view_attachment`: проверенное превью изображения в нативном формате MCP image
- `add_comment`: комментарий в текущую задачу
- `add_attachment`: публикация файла из выделенной папки результатов
- `set_progress`: статус выполнения текущей задачи, например «Сбор информации о проекте» или «Написание кода» (см. ниже)
- `commit_changes`: Git-коммит изменений рабочей папки задачи от имени агента (см. [Коммиты агента](execution.md#коммиты-агента))

Все пять инструментов чтения принимают необязательный `task_id`: полный UUID либо короткий ID из карточки или доски (6–8 символов, регистр не важен). Без него читается текущая задача. Например, из задачи `CBD78596` агент может вызвать `get_task({"task_id":"D91B14AC"})`, затем передать полный `task.id` из ответа в `list_comments`, `list_attachments`, `read_attachment` и `view_attachment`. Переносить описание и файлы между задачами не требуется. Если короткий ID совпадает у нескольких задач, нужен полный UUID. Архивные задачи также доступны для чтения.

`get_task` возвращает `task` с описанием, расписанием, работником, тегами и этапами, `attachments` (до 20 файлов), `attachment_count` и `next_offset` для продолжения через `list_attachments`. Описание, граница истории комментариев и список файлов другой задачи фиксируются при первом обращении к ней в текущем вызове CLI. Собственные изменения карточки через инструменты управления обновляют её метаданные в `get_task`, сохраняя снимки входных файлов и истории. Чтение не меняет исходную задачу и не добавляет её файлы к входам текущего запуска. `add_comment`, `add_attachment`, `set_progress` и `commit_changes` продолжают работать только с текущей задачей и её рабочей папкой.

`list_comments` принимает `offset` (по умолчанию 0) и `limit` (1–20, по умолчанию 20). Ответ содержит `comments` и `next_offset`: передавайте полученное смещение в следующий запрос, пока оно не станет `null`. Для длинных сообщений страница может содержать меньше запрошенного числа комментариев, чтобы уложиться в лимит ответа. Чтение истории не создаёт комментариев и не запускает задачу.

У вложений комментария есть `id`, имя, MIME-тип, размер, признак превью и `available`. Для `available: true` передайте `id` как `attachment_id` в `read_attachment` или `view_attachment`; для другой задачи также передавайте её `task_id`. В текущей задаче файлы вне снимка входных данных запуска помечены `available: false`, в том числе при явном указании её ID. Новые комментарии текущей задачи после начала вызова CLI и другой задачи после первого обращения к ней появятся в истории следующего вызова.

### Статус выполнения

Пока агент работает, он сам сообщает, чем занят: вызывает `set_progress({"status":"Сбор информации о проекте"})` в начале хода и при каждой смене этапа, например «Написание кода» или «Запуск тестов». Протокол задачи просит агента делать это коротко, на языке задачи. Статус показывается отдельно от основного статуса задачи: строкой с индикатором на карточке доски, под названием в режиме **Список** и в шапке открытой задачи вместе со временем обновления. Каждая смена записывается в **Логи** как «Статус выполнения: …», комментарий при этом не создаётся.

Статус — одна строка до 120 символов: переносы строк и управляющие символы заменяются пробелами, пустая или слишком длинная строка отклоняется. Он ничего не меняет в жизненном цикле: не завершает задачу и не влияет на автопилот. Статус виден только во время хода, в котором его задали. После ответа агента, ошибки, отмены или перехода к следующему этапу сложной задачи строка исчезает, а следующий ход или этап начинает без статуса, пока агент не задаст новый. Вызов из завершённого или заменённого хода отклоняется. В API статус приходит в `latestRun.progress` задачи и в `progress` запуска (`{ text, updatedAt }` или `null`); `get_run` и `list_runs` в MCP возвращают его так же. Демо-агент задаёт статус «Демо: выполнение задачи».

Папку результатов brigd создаёт внутри рабочего проекта и сообщает агенту в контексте запуска. Агент сохраняет туда скриншот или отчёт, затем вызывает `add_attachment`. Инструмент не принимает произвольный путь к домашней папке или другим файлам проекта. Символические ссылки, жёсткие ссылки, специальные файлы и выход за пределы папки результатов отклоняются.

Помощник привязан к конкретной задаче, запуску, ходу, этапу и попытке. После отмены, завершения или перехода к другому ходу прежние вызовы больше не могут публиковать файлы и комментарии. Проверка актуальности и запись в базу выполняются в одной транзакции.

Разрешены только точные имена этих инструментов brigd. Режимы безопасности CLI сохраняются: Codex использует `workspace-write` с доступом к сети и `on-request`, Claude Code использует `default`. Другие MCP-серверы и пользовательские правила не заменяются. Вложения, имена файлов и комментарии являются входными данными, а не разрешением обойти защиту CLI. Если нативные разрешения мешают создать нужный результат, агент должен вернуть статус `blocked` с объяснением.

Защищённая публикация использует Linux `/proc/self/fd`, поэтому целевая среда этой версии — Linux, в том числе Docker-контейнер. При отсутствии нужной поддержки запуск останавливается с ошибкой, не переходя к менее защищённому чтению файлов.

Для каждой публикации агент передаёт `idempotency_key` и повторяет тот же ключ при повторной попытке. Одинаковый запрос возвращает сохранённый результат; другой текст или файл с тем же ключом отклоняется. Локальные папки `.brigd-inputs-*` и `.brigd-outbox-*` не предназначены для коммита в Git. Неизменённые временные копии входных файлов удаляются при закрытии помощника; созданные агентом результаты остаются в папке запуска, пока она существует: после переноса результата в целевую ветку worktree удаляется вместе с ними (см. [execution.md](execution.md)), поэтому файлы, которые нужно сохранить, агент публикует как вложения.

## Управление приложением через MCP

Можно поставить агенту задачу «создай карточки по плану, назначь работников, заархивируй старые и сделай бэкап». Для этого доступны 66 дополнительных инструментов:

| Раздел | Инструменты |
| --- | --- |
| Карточки | `list_tasks`, `create_task`, `update_task`, `archive_task`, `restore_task`, `set_task_tags`, `post_task_comment` |
| Запуски | `start_task`, `followup_task`, `list_runs`, `get_run`, `get_run_diff`, `resume_run`, `retry_run`, `cancel_run`, `integrate_run`, `skip_integration`, `cancel_integration`, `reconcile_run` |
| Работники | `list_workers`, `get_worker`, `create_worker`, `update_worker`, `archive_worker`; восстановление — `update_worker` с `data.archived: false` |
| Инструкции, теги, модели | `list_*`, `get_*`, `create_*`, `update_*`, `delete_*` для `instructions`/`instruction`, `tags`/`tag` и `models`/`model` |
| Настройки | `get_app_info`, `get_general_settings`, `update_general_settings`, `get_permission_settings`, `update_permission_settings`, `get_autopilot_settings`, `update_autopilot_settings`, `get_check_triage_settings`, `update_check_triage_settings`, `get_result_transfer_settings`, `update_result_transfer_settings`, `get_concurrency_settings`, `update_concurrency_settings`, `get_autopilot`, `update_autopilot`, `move_autopilot_task`, `get_integrator`, `update_integrator`, `get_cli_config`, `configure_cli` |
| Бэкапы | `list_backups`, `create_backup`, `rename_backup`, `set_backup_auto_update`, `delete_backup`, `restore_backup` |
| Документация | `list_doc_pages`, `search_doc_pages`, `get_doc_page`, `create_doc_page`, `update_doc_page`, `delete_doc_page` |

Списки управления принимают `offset` и `limit` (до 20), возвращают `items`, `total` и `next_offset`. `search_doc_pages` принимает `query` и возвращает до 20 страниц с фрагментом текста, где совпадения заключены в квадратные скобки. `get_doc_page` отдаёт страницу в Markdown вместе с `childIds`; `create_doc_page` и `update_doc_page` принимают `data.title`, `data.parentId` и `data.markdown`, при этом `update_doc_page` заменяет содержимое целиком. `list_tasks` дополнительно принимает `query`, `tag_id` и `archived`: `active`, `archived` или `all`. Списки содержат краткие записи; описание карточки и полные профили читаются отдельными инструментами. `get_autopilot` также принимает `offset` и `limit`, возвращает краткие массивы `pool` и `attempts`, их размеры `pool_count`/`attempt_count` и смещения `pool_next_offset`/`attempts_next_offset`.

Каждая команда изменения требует `idempotency_key`. Поля создаваемой или редактируемой сущности передаются в `data`, идентификатор — в `task_id`, `run_id`, `worker_id` и т. п. Например:

```json
{"tool":"create_task","arguments":{"data":{"title":"Проверить отчёт","instruction":"Проверить цифры и приложить результат."},"idempotency_key":"report-card-1"}}
{"tool":"archive_task","arguments":{"task_id":"D91B14AC","idempotency_key":"archive-old-report"}}
{"tool":"create_backup","arguments":{"idempotency_key":"backup-after-planning"}}
```

Новая карточка наследует исходную рабочую папку проекта и провайдера агента, по умолчанию получает ручной запуск и не стартует автоматически. В `data` можно задать другой существующий `cwd`, работника, расписание, теги, этапы и режим `ultracode` (`true`, `false` или `null` — по профилю работника). Для выполнения используйте `start_task`; для дополнительного запроса в сохранённую сессию — `followup_task`. Изменение настроек работников и приложения не переписывает уже начавшиеся запуски.

Квитанции команд компактны. Повтор с тем же ключом и аргументами возвращает сохранённую квитанцию, в том числе при повторном подключении помощника к тому же ходу. Другие аргументы с прежним ключом отклоняются. Если выполнение прервалось без сохранённого результата, помощник предлагает проверить состояние приложения, а не создавать дубликат с новым ключом.

Действуют те же ограничения, что в интерфейсе: активную карточку нельзя архивировать до завершения или отмены запуска, завершённая работа продолжается дополнительным запросом, слияние требует настроенных проверок. Команды выполняются внутри сервиса; агенту не нужен доступ к SQLite, произвольным HTTP-адресам или конфигурации сервера.

Бэкап содержит базу brigd: карточки, историю, вложения и настройки. Исходники рабочих проектов и сессии CLI в него не входят. `restore_backup` заменяет базу, создавая защитную копию прежних данных, и останавливает работающих агентов. Он и отмена собственного запуска сначала возвращают `accepted: true, status: "queued"`; выполнение начинается после доставки ответа MCP. Это подтверждение принятия, а не завершённого восстановления. Управление доступно до завершения, отмены или смены хода агента.

## Ограничения

| Ограничение | Значение |
| --- | --- |
| Один файл | 10 МиБ |
| Файлы в одном списке задачи, комментарии или уточнении | 20 |
| История файлов одной задачи | 200 файлов / 200 МиБ |
| Незавершённые загрузки | 100 файлов / 100 МиБ |
| Срок незавершённой загрузки | 24 часа |
| Общий объём вложений | 1 ГиБ |
| Превью для MCP | Не более 256 КиБ |
| Вызовы MCP за один ход | 256 |
| Один запрос MCP | 256 КиБ |
| Один ответ MCP | 384 КиБ |
| Все ответы MCP за один ход | 1,5 МиБ |

Превью уменьшено отдельно от оригинала, чтобы изображение помещалось в ограниченные JSONL-события CLI. Количество и общий объём ответов MCP ограничены. Эти пределы не отменяют отдельные ограничения CLI на вывод и время работы.

## Хранение и обновление

Исходные файлы, безопасные превью, метаданные и снимки сохраняются в той же SQLite-базе, что задачи. Списки задач и комментариев возвращают только метаданные, без содержимого файлов. Миграция добавляет таблицы и сохраняет существующие задачи, историю, работников и ID сессий.

Путь к базе и переменные `BRIGD_` / `TRACKT_` совместимы с прежними установками. Для контейнера продолжайте использовать существующие тома и [инструкцию резервного копирования](container.md). Не удаляйте том базы при обновлении.

В production-образ входят MCP-помощник и зависимости обработки изображений. `bun run build` также собирает stdio-помощник. Проверки проекта используют синтетические события и MCP-клиент без оплачиваемых вызовов моделей; это не заменяет проверку авторизованной сессии конкретного провайдера.
