# Подключение к brigd из IDE через MCP

Для обычного поручения «поставь задачи таким-то сотрудникам» локальному агенту **не требуется настраивать MCP**. В этом репозитории есть инструкции `AGENTS.md` и помощник `bun run brigd`: агент сам читает сотрудников и создаёт назначенные карточки через API запущенного приложения. Пользователь просто формулирует задание. Если агент работает внутри brigd, инструменты уже подключены автоматически. Приведённая ниже настройка нужна для отдельного MCP-клиента, который не может воспользоваться локальными командами.

Запущенный brigd предоставляет отдельный MCP по адресу `http://127.0.0.1:4310/mcp`. Транспорт — **Streamable HTTP**, авторизация — **Bearer token**. Можно читать и создавать задачи, работать с документацией и управлять приложением без запуска задачи или агента внутри brigd.

## Включение

Сгенерируйте постоянный случайный токен:

```sh
openssl rand -hex 32
```

Сохраните полученное значение в `.env.local` в корне установки brigd:

```dotenv
BRIGD_MCP_TOKEN=<полученный токен>
```

Перезапустите brigd обычным способом. Для запуска исходников без проверки обновлений используйте `bun run start:local`; для разработки — `bun run dev`. Bun загружает `.env.local` автоматически. Если файл `dist/` ещё не собран, для обычного интерфейса сначала выполните `bun run build`.

Адрес использует порт сервера (`PORT`, по умолчанию `4310`), а не порт Vite `5173`. Без токена или при пустом значении `/mcp` возвращает `404`. Допустимы 32–256 символов `A–Z`, `a–z`, `0–9`, `_`, `-`; пример выше создаёт 64 шестнадцатеричных символа. Поддерживается и прежний префикс `TRACKT_MCP_TOKEN`, но явно заданный `BRIGD_MCP_TOKEN`, включая пустой, имеет приоритет.

Токен даёт доступ к управлению приложением, включая запуск задач, настройки и бэкапы. Он передаётся только заголовком `Authorization: Bearer …`; параметры URL для авторизации не используются. `.env.local` исключён из Git. Для смены или отключения токена измените переменную и перезапустите сервис.

## Codex CLI и расширение IDE

Добавьте в `~/.codex/config.toml`:

```toml
[mcp_servers.brigd]
url = "http://127.0.0.1:4310/mcp"
bearer_token_env_var = "BRIGD_MCP_TOKEN"
```

Либо зарегистрируйте тот же сервер командой:

```sh
codex mcp add brigd --url http://127.0.0.1:4310/mcp --bearer-token-env-var BRIGD_MCP_TOKEN
```

Переменная `BRIGD_MCP_TOKEN` должна быть доступна **процессу Codex или IDE** и содержать то же значение, что у сервера. Запись в `.env.local` brigd сама по себе не экспортирует переменную в уже запущенную IDE. Например, задайте её в терминале и запустите Codex или IDE из этого терминала:

```sh
export BRIGD_MCP_TOKEN='<тот же токен>'
codex
```

После изменения настроек откройте новую сессию. `codex mcp list` покажет зарегистрированный сервер; для проверки соединения попросите агента: «Через brigd вызови `get_app_info` и покажи список задач». Настройки соответствуют [официальной документации Codex по MCP](https://learn.chatgpt.com/docs/extend/mcp).

В другом MCP-клиенте выберите Streamable HTTP, URL `http://127.0.0.1:4310/mcp` и заголовок `Authorization: Bearer <тот же токен>`. OAuth и отдельный SSE endpoint здесь не используются.

## Доступные инструменты

Доступны [инструменты управления приложением](attachments.md#управление-приложением-через-mcp) и пять инструментов чтения: `get_task`, `list_comments`, `list_attachments`, `read_attachment`, `view_attachment`.

- В инструментах чтения `task_id` обязателен: полный UUID либо однозначный короткий ID из интерфейса. Данные читаются на момент каждого запроса. Списки возвращают `next_offset` для следующей страницы.
- `create_task` по умолчанию использует рабочую папку из общих настроек brigd, провайдер Codex и ручное расписание. Можно передать `data.cwd`, `data.provider`, `data.workerId` или `data.priority` (`critical`, `high`, `normal`, `low`; по умолчанию `normal`). Для запуска по времени передайте `data.schedule: "daily"`, `data.timeOfDay` (`"02:00"`), `data.weekdays` (1 — понедельник, 7 — воскресенье; без поля — каждый день) и `data.timeZone` пользователя (например `"Europe/Moscow"`; без поля сохраняется пояс сервера, в контейнере обычно UTC). Создание карточки не запускает её. Автопилот берёт карточки с более высоким приоритетом первыми; `move_autopilot_task` переставляет карточку только среди карточек того же приоритета, а между приоритетами её переносит `update_task` с новым `data.priority`.
- Для комментария используйте `post_task_comment` с явным `task_id`. `add_comment`, `add_attachment`, `set_progress`, `commit_changes` и запись оригинала вложения на сервер через `materialize` остаются доступны только соответствующим агентам задач; у внешнего клиента нет текущего запуска и его рабочей папки.
- Изменения требуют `idempotency_key`. Используйте новый UUID для каждого действия и сохраняйте тот же ключ и аргументы при повторе. Ключи общие для клиентов с одинаковым токеном; результаты сохраняются в базе и переживают переподключение и перезапуск. Изменённые аргументы с прежним ключом отклоняются. Если операция принята, но результат не сохранён, сначала проверьте состояние приложения.
- `restore_backup` возвращает `accepted: true, status: "queued"`; это подтверждение принятия. Во время восстановления возможен `503`. После него клиент продолжает работать с восстановленной базой. Вместе с базой откатывается история выполненных MCP-операций: проверяйте фактическое состояние перед повтором старых действий.

Каждый HTTP POST содержит одно JSON-RPC сообщение, до 256 КиБ; результат инструмента ограничен 384 КиБ. Одновременно принимается до 16 HTTP-запросов. Протокол не хранит сессии: отдельные GET/SSE-подписки и DELETE сессии возвращают `405`, при этом обычный MCP-клиент работает через POST.

Встроенный MCP задач через stdio по-прежнему подключается автоматически и не требует этого токена.

## Docker и диагностика

`compose.yaml` передаёт `BRIGD_MCP_TOKEN` в контейнер. Укажите его в окружении Compose либо запустите `docker compose --env-file .env.local up -d --build`. Порт остаётся опубликован на loopback хоста; `data.cwd` должен указывать папку **внутри контейнера**. Если клиент и brigd находятся на разных машинах, `127.0.0.1` клиента не указывает на сервер: нужен доступ к серверу, например через перенаправление порта SSH.

| Ответ | Что проверить |
| --- | --- |
| `404` | Токен задан серверу; процесс перезапущен с новой версией кода; запрос идёт на `/mcp` серверного порта. |
| `401` | Клиент передаёт тот же токен в заголовке Bearer; переменная доступна процессу IDE. |
| `403` | Host и, если отправлен, Origin входят в `BRIGD_ALLOWED_HOSTS` / `BRIGD_ALLOWED_ORIGINS`. Запросы браузера с `Sec-Fetch-Site: cross-site` запрещены. |
| `405` при открытии URL в браузере | Браузер выполняет GET. Проверяйте подключение MCP-клиентом через Streamable HTTP. |
| `429` | Дождитесь завершения других запросов и повторите с тем же ключом операции. |
| `503` | Сервис запускается, останавливается или восстанавливает бэкап. |

Проверки Host и Origin веб-интерфейса сохраняются. Bearer-токен разрешает запросы без Origin только на `/mcp`; обычные изменяющие `/api/*` запросы по-прежнему требуют Origin интерфейса.
