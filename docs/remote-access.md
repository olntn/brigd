# Удалённое управление через ретранслятор (концепция)

> **Статус:** концепция для обсуждения, не реализовано. В текущей версии brigd удалённого доступа нет: сервис слушает только `127.0.0.1`, и публиковать его в интернет нельзя (см. [README → Разрешения и безопасность](../README.md#разрешения-и-безопасность)).

## Задача

brigd и все агенты работают на компьютере пользователя: CLI, вход в аккаунты, репозитории, worktree, база SQLite, команды проверки. Пользователь разворачивает на сервере с публичным адресом небольшой сервис-ретранслятор (**brigd relay**). С телефона или чужого компьютера он открывает адрес ретранслятора и управляет задачами: смотрит доску, отвечает на вопросы агентов, ставит и запускает задачи, включает автопилот. Вычисления и данные остаются на локальной машине.

Что сюда **не входит**:

- Выполнение задач на сервере. Ретранслятор не запускает CLI и не хранит задачи, комментарии, вложения и код.
- Пробуждение компьютера. Если компьютер спит или brigd остановлен, ретранслятор показывает «не в сети», а расписание не работает, как и сейчас.
- Многопользовательский режим. Владелец один, просто у него несколько устройств.

## Отправные точки в текущем коде

Концепция опирается на то, как brigd устроен сейчас:

1. **Нет авторизации, защита держится на loopback.** `createHandler` проверяет `Host`, `Origin` и `Sec-Fetch-Site` (`server/http.ts:90`), а любые изменения требуют Origin локального интерфейса (`server/http.ts:97`). Обычный reverse proxy пришлось бы настроить на подмену Host/Origin, а это фактически отключает защиту от CSRF. Поэтому нужен отдельный удалённый вход со своей проверкой прав, а не «проброс порта».
2. **Интерфейс работает только через запрос-ответ.** UI обращается к API относительными `fetch('/api/...')` и опрашивает сервер каждые 2 секунды, пока вкладка видима (`src/App.svelte:483`). WebSocket и SSE нет. Поэтому интерфейс можно пропустить через туннель, ничего в нём не меняя.
3. **Все программные изменения уже проходят через одну точку.** Инструменты управления MCP (и у агентов внутри задач, и у внешнего `/mcp`) вызывают `AppAccess.request`, который собирает `Request` с внутренними Host/Origin и передаёт его в `createHandler` (`server/index.ts:107`, `server/task-mcp-app.ts:161`). Политика прав, встроенная в этот обработчик, автоматически распространяется и на MCP.
4. **Управление задачами по сути означает выполнение кода.** По умолчанию CLI работают в полном доступе. `BRIGD_INTEGRATION_CHECKS` — произвольные команды. `/api/cli-config` правит `~/.claude` и `~/.codex`, бэкапы содержат всю базу и заменяют её. Тот, кто может поставить и запустить задачу, может выполнить код на компьютере пользователя. Этот факт определяет модель безопасности ниже.

## Архитектура

```
 Телефон / ноутбук                  Сервер (VPS)                         Компьютер пользователя
┌──────────────────┐  HTTPS   ┌──────────────────────────┐  WSS (исходящее ┌───────────────────────────────┐
│ браузер: обычный │ ───────► │ brigd relay              │ ◄────────────── │ brigd                         │
│ интерфейс brigd  │          │ • TLS, проверка подписи  │   соединение)   │ • коннектор ретранслятора     │
│                  │          │   токена на входе        │                 │ • удалённый доступ: устройства │
│ MCP-клиент       │ ───────► │ • мультиплексирование    │ ═══ туннель ═══ │   токены, политика прав       │
│ (необязательно)  │  /mcp    │   запросов в туннель     │                 │ • createHandler(engine)       │
└──────────────────┘          │ • страница «не в сети»   │                 │ • очередь, CLI, SQLite, Git   │
                              │ • без данных задач       │                 └───────────────────────────────┘
                              └──────────────────────────┘
```

Основные решения:

- **Соединение открывает локальный brigd.** Он устанавливает исходящее WebSocket-соединение `wss://` к ретранслятору. На компьютере не открываются порты, NAT и белый IP не нужны, локальный слушатель по-прежнему привязан к `127.0.0.1`.
- **Ретранслятор работает как транспорт.** Он не понимает API brigd и не хранит его данные. Он только проверяет, можно ли пропустить запрос к компьютеру, и пересылает его. Протокол туннеля версионируется отдельно от API, поэтому обновление brigd не требует обновлять ретранслятор.
- **Интерфейс приходит с компьютера, а не с сервера.** Статические файлы `dist/` тоже идут через туннель, поэтому версия интерфейса всегда совпадает с версией API. Ретранслятор может кэшировать только неизменяемые файлы с хэшем в имени (`/assets/*`), чтобы показать оболочку и сообщение «не в сети» без связи с компьютером.
- **Права выдаёт и проверяет локальный brigd.** Он владеет ключом устройства и сам выпускает удалённые сессии. Ретранслятор умеет проверить подпись токена, но не может создать новый токен.

## Компоненты

### brigd relay (сервер)

Небольшой сервис на Bun без зависимостей от `Store` и `Engine`, в том же репозитории (общий модуль протокола, общие тесты). Запускается отдельным образом Docker или командой `bun run relay`.

- `GET/POST /*` от браузера: проверка токена (см. ниже) и пересылка в туннель.
- `GET /connect` (WebSocket): подключение коннектора, вход по challenge-response.
- `POST /pair`: одноразовая привязка компьютера.
- `/enroll`: собственная страница ретранслятора для добавления нового устройства. Это единственный путь, доступный без токена, и он ограничен по частоте запросов.
- Состояние ретранслятора (`relay-data/relay.json`): публичный ключ привязанного компьютера, список отозванных сессий, время последней связи. Задачи, тексты и файлы ретранслятор не хранит. В журналы попадают метод, шаблон маршрута, статус и длительность, но не тела, не query string (в `?name=` бывают имена файлов) и не cookie.
- TLS: проще всего поставить перед ретранслятором Caddy с автоматическим сертификатом. Можно использовать и свой reverse proxy. Нужны домен и порт 443, ресурсов хватит минимальных (1 vCPU, 256 МБ).

### Коннектор (в процессе brigd)

Новый модуль `server/relay-client.ts`, работающий в том же процессе, что и сервер. Отдельный процесс пришлось бы подключать к `127.0.0.1` с поддельными Host/Origin, и удалённый запрос стал бы неотличим от локального.

- Запускается в `activate()` и останавливается в `shutdown()` и при паузе восстановления (`server/index.ts:192`, `:203`, `:59`). Жизненный цикл тот же, что у `BackupAutoUpdater`.
- Удалённые запросы учитываются в общем счётчике `requests`, чтобы восстановление бэкапа дожидалось их так же, как локальных. Во время восстановления они получают тот же `503`.
- Переподключается с экспоненциальной задержкой от 1 до 60 секунд со случайным разбросом. Ping отправляется каждые 25 секунд, ретранслятор считает компьютер недоступным через 60 секунд без ответа.
- Для каждого запроса проверяет удалённую сессию, собирает `Request` с внутренними Host/Origin (как в `AppAccess.request`) и вызывает обработчик с контекстом `remote: { sessionId, scope }`. Контекст передаётся внутри процесса, а не HTTP-заголовком, поэтому подделать его снаружи нельзя.

### Удалённый доступ (локальное состояние и политика)

Новый модуль `server/remote-access.ts`:

- Ключ устройства Ed25519 (`data/remote-device.key`, права `0600`) и привязка к ретранслятору.
- Список устройств и сессий: название, область прав, дата выпуска, последняя активность, отзыв. Хранятся только хэши токенов.
- Журнал удалённых действий: время, устройство, метод, шаблон маршрута, статус.
- Таблица «маршрут → требуемая область» (см. «Права»).

Всё это хранится **вне основной базы**, в `data/remote-access.sqlite` или JSON-файле, и не попадает в бэкапы. Иначе восстановление старого бэкапа вернуло бы отозванные устройства, а скачанный бэкап содержал бы данные сессий.

## Протокол туннеля

Одно WebSocket-соединение с мультиплексированием запросов и сжатием кадров.

**Вход коннектора:**

1. Ретранслятор отправляет `{type:"challenge", nonce, relayId}`.
2. Коннектор отвечает `{type:"hello", protocol:1, deviceId, brigdVersion, sig}`, где `sig` — подпись Ed25519 над `"brigd-relay-v1" ‖ relayId ‖ nonce`.
3. Ретранслятор проверяет подпись ключом, сохранённым при привязке. Новое подтверждённое подключение того же устройства заменяет старое.

**Запросы** (управляющие кадры — JSON, тела — двоичные кадры `[u32 streamId][u8 flags][≤ 64 КиБ данных]`):

| Кадр | Направление | Содержимое |
| --- | --- | --- |
| `req` | relay → brigd | `id`, `method`, `path` с query, разрешённые заголовки, токен сессии |
| `res` | brigd → relay | `id`, `status`, разрешённые заголовки |
| двоичный кадр | в обе стороны | часть тела; флаг `end` завершает тело |
| `cancel` | в обе стороны | браузер ушёл или превышен тайм-аут |
| `revoked` | brigd → relay | ID отозванной сессии, ретранслятор отклоняет её на входе |
| `ping` / `pong` | в обе стороны | проверка связи |

Ограничения: до 16 одновременных запросов (как у внешнего MCP), лимиты тел те же, что локально (`ATTACHMENT_MAX_BYTES` = 10 МиБ для вложений), обратное давление через буфер WebSocket, тайм-аут запроса 120 секунд.

**Заголовки** передаются по белым спискам. От браузера: `content-type`, `content-length`, `accept`, `if-none-match`, `user-agent` (для названия устройства), cookie `brigd_remote`. Обратно: `content-type`, `content-length`, `content-disposition`, `cache-control`, `etag`, CSP и остальные `securityHeaders`, `cross-origin-resource-policy`, `set-cookie` только для `brigd_remote`. HSTS добавляет ретранслятор.

**Потерянный ответ.** Ретранслятор никогда не повторяет запросы, кроме GET. Если туннель оборвался во время изменения, браузер получает `504` с текстом «Результат неизвестен: проверьте доску перед повтором». Это то же правило, что у `bun run brigd`: при потере ответа сначала проверить список, чтобы не создать дубликат.

## Аутентификация и сессии

Источник доверия — локальный brigd. Ретранслятор не хранит паролей пользователя и не выпускает сессии.

### 1. Привязка ретранслятора (один раз)

1. При первом запуске на сервере ретранслятор выводит одноразовый код привязки (действует 15 минут). Новый код можно получить командой `docker compose exec relay brigd-relay pairing-code`.
2. На компьютере: **Настройки → Удалённый доступ → Подключить ретранслятор**, ввести адрес `https://relay.example.com` и код.
3. brigd создаёт ключ Ed25519 и отправляет публичный ключ с кодом на `POST /pair` по HTTPS. Подлинность сервера подтверждает обычная проверка сертификата. Ретранслятор сохраняет ключ, после чего коннектор подключается.
4. Перепривязка требует нового кода на сервере, поэтому увести ретранслятор без доступа к серверу нельзя.

### 2. Добавление устройства

1. На компьютере: **Удалённый доступ → Добавить устройство**. Нужно выбрать область прав (по умолчанию «Управление задачами»). brigd показывает QR-код и ссылку `https://relay.example.com/enroll#<одноразовый код>`, действующую 10 минут. Код передаётся во фрагменте `#`, поэтому не попадает в журналы сервера.
2. Телефон открывает ссылку. Страница ретранслятора отправляет код запросом `POST /enroll`, ретранслятор пересылает его в туннель.
3. brigd проверяет и гасит код, создаёт сессию и возвращает cookie `brigd_remote` с флагами `HttpOnly; Secure; SameSite=Strict; Path=/`.
4. На локальном экране появляется уведомление «Подключено новое устройство: Safari, iPhone». Добавить устройство можно с компьютера, а также с уже подключённого устройства, если у него есть право «Управление доступом».

### 3. Токен сессии

`base64url(payload).base64url(подпись)`, где `payload = {v:1, sid, scope, iat, exp}`, а подпись делается ключом устройства.

- **Ретранслятор** проверяет подпись и срок, сверяется со списком отзыва и только после этого пропускает запрос в туннель. Запросы без токена из интернета до компьютера не доходят.
- **brigd** повторно проверяет подпись, срок и то, что сессия существует и не отозвана, учитывает таймаут бездействия и применяет область прав.
- Срок: 30 дней абсолютно и 7 дней без активности. Когда прошло больше половины срока, brigd незаметно выдаёт новый cookie.
- Cookie выбран потому, что `<img src="/api/tasks/.../attachments/...">` и аватары не умеют отправлять заголовки. Защита от CSRF: `SameSite=Strict`, ретранслятор требует для изменений `Origin` = свой публичный адрес и отклоняет `Sec-Fetch-Site: cross-site`, коннектор подставляет внутренний Origin только после этих проверок.

### 4. Отзыв и аварийное отключение

- Отзыв конкретного устройства в списке на компьютере срабатывает сразу: brigd отклоняет сессию и отправляет `revoked` ретранслятору.
- Переключатель «Удалённый доступ выключен» закрывает туннель. Переменная `BRIGD_REMOTE=off` запрещает его при запуске, например на время отладки.
- На сервере `brigd-relay block` отклоняет все запросы, пока компьютер недоступен. Это нужно, если телефон потерян, а до компьютера не добраться.

### 5. Удалённый MCP (этап 2)

`https://relay.example.com/mcp` пересылается в локальный `/mcp`. Вместо общего `BRIGD_MCP_TOKEN` используется подписанный токен устройства типа `mcp` с областью прав. Сам `BRIGD_MCP_TOKEN` остаётся локальным. Так как инструменты MCP идут через `createHandler`, область прав применяется к ним автоматически.

## Права удалённого доступа

Каждый маршрут API относится к одной из областей. Политика **запрещает всё, что не разрешено явно**: маршрут, который не внесён в таблицу, доступен только локально. Тест проверяет, что каждый маршрут из `server/http.ts` классифицирован.

| Область | Что разрешено | Маршруты (примерно) |
| --- | --- | --- |
| **Просмотр** | Доска, карточки, комментарии, логи, вложения, документация, автопилот, diff запуска | `GET /api/info`, `/api/tasks*`, вложения, `/api/workers`, `/api/tags`, `/api/models`, `/api/instructions`, `/api/docs*`, `/api/autopilot`, `/api/runs/:id/diff`, аватары, статика |
| **Управление задачами** (по умолчанию) | Всё из просмотра, плюс создание и правка карточек, комментарии и ответы на вопросы, запуск, отмена, повтор, продолжение, дополнительные запросы, слияние, архив, теги, загрузка вложений, автопилот вкл./выкл., правка документации | `POST/PATCH /api/tasks*`, `/api/runs/:id/*`, `/api/uploads*`, `PATCH /api/autopilot`, запись `/api/docs*`, `/api/tags*` |
| **Администрирование** (только локально, пока не разрешено явно для конкретного устройства) | Работники, модели, общие инструкции, Интегратор, все настройки (разрешения, команды проверки, параллельность, общие), настройка CLI, хранилище, бэкапы, управление доступом | `/api/workers*` (изменение), `/api/avatars` POST, `/api/models*` (изменение), `/api/instructions*` (изменение), `/api/integrator` PATCH, `/api/settings/*`, `/api/cli-config*`, `/api/backups*`, `/api/remote/*` |

Дополнительные правила:

- **Проекты.** Удалённо созданная или изменённая карточка может использовать только известные рабочие папки: папку по умолчанию, папки существующих неархивных задач и явный список в настройках удалённого доступа. Так украденная сессия не направит агента в произвольный каталог одним полем `cwd`.
- **Происхождение задач.** Если задачу создали или изменили её поручение удалённо, она помечается. MCP-доступ её запусков (`TaskAppAccess`) ограничивается областью удалённой сессии, пока владелец не подтвердит задачу локально. Иначе можно было бы обойти запрет так: «поставь задачу, в которой агент через `update_autopilot_settings` заменит команды проверки». Метка нужна именно на задаче, а не на запуске: удалённо можно перевести задачу на интервал, и следующий запуск сделает уже локальный планировщик.
- **Честная оговорка.** В режиме полного доступа агент может обойти ограничения MCP, просто отредактировав файлы, к которым у пользователя сервиса есть права. Поэтому области прав защищают от ошибок, случайных действий и ограниченно скомпрометированных клиентов, но не являются жёсткой границей. Жёсткую границу даёт только ограниченный режим CLI. Для этого в политике есть опция **«Удалённые задачи запускать в ограниченном режиме»** (по умолчанию выключена: большинство пользователей работает в полном доступе, и без него удалённый доступ потерял бы смысл).

## Модель угроз

| Угроза | Чем закрывается |
| --- | --- |
| Сканеры и перебор паролей из интернета | Без подписанного токена запрос не уходит дальше ретранслятора. Открыт только `/enroll`, где действует лимит частоты и одноразовые коды на 128 бит. Локальный порт не публикуется. |
| Украденный телефон или cookie | Сроки и таймаут бездействия, мгновенный отзыв с компьютера, `brigd-relay block`, область прав устройства. Этап 2: подтверждение passkey перед опасными действиями. |
| Взлом сервера ретранслятора | Ретранслятор видит трафик открытым (TLS заканчивается на нём), может подменить JS и действовать от имени активных сессий. Создать новые токены он не может, потому что ключа у него нет. Ущерб ограничен областью прав (администрирование по умолчанию недоступно удалённо) и списком проектов. Полная защита возможна только при сквозном шифровании (этап 3). Поскольку сервер свой, в MVP ему доверяют так же, как SSH-доступу к нему. |
| Подмена ретранслятора для коннектора | WebPKI-проверка TLS и адрес, сохранённый при привязке. Ретранслятор не может выдать себя за компьютер, так как не знает его ключ. |
| Повтор и перехват входа коннектора | Новый `nonce` при каждом подключении, подпись включает `relayId`. |
| CSRF через адрес ретранслятора | `SameSite=Strict`, проверка Origin и `Sec-Fetch-Site` на ретрансляторе, внутренний Origin подставляется только после авторизации. |
| XSS из содержимого задач | Сохраняются текущий CSP и песочница вложений (`default-src 'none'; sandbox`). С публичным адресом их значение растёт, поэтому любые послабления CSP запрещены. |
| Восстановление старого бэкапа «воскрешает» отозванные устройства | Состояние удалённого доступа хранится вне основной базы и бэкапов. |
| Перегрузка компьютера через туннель | До 16 одновременных запросов, лимиты тел, лимит частоты на ретрансляторе, тайм-ауты. |
| Агент задачи читает ключ устройства | Агенты работают от того же пользователя, и права файлов от них не защищают (как и сейчас с базой). Ущерб: агент может выдать себя за компьютер перед ретранслятором. Это не расширяет его возможности, ведь код на компьютере он уже выполняет. Токены сессий хранятся только как хэши. |
| Утечка данных через журналы сервера | В журналы пишутся только метаданные, без тел, query string и cookie. |

## Интерфейс

**На компьютере** появляется раздел **Настройки → Удалённый доступ**:

- Состояние: «Подключено к relay.example.com · 45 мс» или «Нет связи с ретранслятором, повтор через 30 с».
- Кнопки «Подключить ретранслятор» и «Добавить устройство» (QR-код).
- Список устройств: название, область прав, последняя активность, адрес по данным ретранслятора, «Отозвать».
- Политика: области прав, проекты, опция ограниченного режима для удалённых задач.
- Журнал удалённых действий и главный переключатель.
- В шапке значок «Удалённый доступ: 1 устройство активно», чтобы удалённая активность была видна сразу.

**На удалённом устройстве** открывается тот же интерфейс:

- `/api/info` дополнительно возвращает `remote: { scope, device }`. Недоступные разделы и кнопки скрываются, а сервер всё равно возвращает `403`.
- Если компьютер не в сети, ретранслятор отвечает на `/api/*` JSON `503 {"error": "Компьютер с brigd не в сети (последняя связь 12:03)"}`. Существующая функция `api()` в `App.svelte` показывает поле `error` без изменений.
- Комментарии и ответы, отправленные удалённо, помечаются «через удалённый доступ (iPhone)».

## Трафик

Опрос раз в 2 секунды при большой доске через мобильную сеть получается заметным: при ответе `/api/tasks` в 100 КБ это около 180 МБ в час открытой вкладки. Меры:

- Этап 1: сжатие кадров в туннеле (`permessage-deflate`, если его поддерживают обе стороны Bun, иначе gzip тел в коннекторе) и сжатие ответов браузеру на ретрансляторе. Повторяющийся JSON списка задач сжимается в несколько раз.
- Этап 2: дешёвый ответ «без изменений». Ревизия данных в `Store`, `GET /api/tasks?since=<rev>` возвращает `204`. Альтернатива — ETag. HTTP-кэш браузера для этого не используется, потому что `Cache-Control: no-store` защищает данные на устройстве.

## Развёртывание ретранслятора (набросок)

```yaml
# compose.relay.yaml на сервере
services:
  relay:
    image: brigd-relay:local          # build: { context: ., target: relay }
    environment:
      RELAY_PUBLIC_ORIGIN: "https://relay.example.com"
    volumes: [relay-data:/var/lib/brigd-relay]
    restart: unless-stopped
  caddy:
    image: caddy:2
    command: caddy reverse-proxy --from relay.example.com --to relay:4410
    ports: ["443:443", "80:80"]
    volumes: [caddy-data:/data]
volumes: { relay-data: {}, caddy-data: {} }
```

На компьютере пользователю не нужно ничего настраивать вне интерфейса: адрес и привязка сохраняются в состоянии удалённого доступа. Для контейнера brigd допустимы переменные `BRIGD_RELAY_URL` и `BRIGD_REMOTE=off`. Контейнеру нужен только исходящий доступ в интернет, порт по-прежнему публикуется на `127.0.0.1`.

## Альтернативы

| Вариант | Плюсы | Минусы | Вывод |
| --- | --- | --- | --- |
| Mesh-VPN (Tailscale, WireGuard, ZeroTier) | Сквозное шифрование, без своего кода, без открытых портов | Клиент на каждом устройстве. У brigd нет своей авторизации, поэтому любой участник сети получает весь API, включая администрирование. Нужно настраивать `BRIGD_HOST` и списки Host/Origin. Нет «не в сети», журнала и областей прав. | Годится как временное решение «только для себя» |
| SSH reverse tunnel и reverse proxy с паролем на VPS | Работает уже сейчас | Proxy подменяет Host/Origin, и защита от CSRF фактически снимается. Пароль проверяется только на сервере, весь API доступен. Прямо противоречит README. | Не рекомендуется |
| Cloudflare Tunnel и Access, ngrok | Готовая аутентификация, свой сервер не нужен | Трафик видит третья сторона. Те же проблемы с Host/Origin и правами. | Допустимо, но это не свой ретранслятор |
| **Свой brigd relay** | Исходящее соединение, права выдаёт локальный brigd, области прав, отзыв, «не в сети», журнал, удалённый MCP | Нужно написать ретранслятор, коннектор и модуль прав | **Рекомендуется** |

## План работ

**Этап 1 — MVP (один компьютер, один ретранслятор):**

1. `server/relay-protocol.ts`: кадры, лимиты, версия протокола. Общий модуль ретранслятора и коннектора.
2. `relay/server.ts`, `bun run relay`, цель `relay` в Dockerfile, `compose.relay.yaml`: привязка, вход коннектора, проверка токенов, пересылка, `/enroll`, страница «не в сети», лимиты, журнал без содержимого.
3. `server/remote-access.ts`: ключ, сессии, коды добавления, подпись и проверка токенов, отзыв, журнал. Отдельное хранилище вне базы.
4. `server/http.ts`: `HttpOptions.remote`, таблица «маршрут → область», запрет неклассифицированного, ограничение `cwd`, локальные маршруты `/api/remote/*`. `/api/info` возвращает `remote`.
5. `server/relay-client.ts` и подключение в `server/index.ts` (`activate`, `shutdown`, восстановление, счётчик `requests`). `BRIGD_REMOTE` и `BRIGD_RELAY_URL` в `server/config.ts`.
6. UI: `src/lib/RemoteAccess.svelte` (раздел настроек), значок активности в шапке, скрытие недоступных разделов для удалённой области.
7. Пометка происхождения задачи и ограничение `TaskAppAccess` для её запусков.
8. `docs/remote-access.md` из концепции превращается в инструкцию, плюс раздел в README.

Тесты этапа 1: классификация каждого маршрута (`tests/remote-policy.test.ts`); подпись, срок, отзыв, таймаут бездействия и «восстановление бэкапа не возвращает сессии» (`tests/remote-access.test.ts`); кадры, лимиты, `cancel`, отсутствие повтора изменений и обрыв во время запроса (`tests/relay-protocol.test.ts`); сквозной сценарий «ретранслятор и коннектор в одном процессе» поверх `createHandler` с mock-движком; MCP-эскалация из удалённой задачи отклоняется.

**Этап 2:** удалённый MCP с токенами устройств; ответ «без изменений» вместо полного опроса; Web Push о вопросах, ошибках и автопилоте (компьютер может отправлять push сам, сервер для этого не нужен, а текст уведомлений не содержит данных задач); подтверждение passkey для опасных действий (проверяет локальный brigd, ретранслятор подделать его не может); несколько компьютеров на одном ретрансляторе с выбором в сессии.

**Этап 3 (по необходимости):** сквозное шифрование, при котором ретранслятор видит только шифротекст. Требуется, чтобы код интерфейса загружался не с ретранслятора (установленный PWA с закреплёнными подписанными файлами, расширение или настольная оболочка), иначе подменённый JS обойдёт шифрование. В MVP этот этап не нужен.

## Решения, которые нужно подтвердить

1. **Доверие серверу.** MVP заканчивает TLS на ретрансляторе (свой сервер считается доверенным). Сквозное шифрование откладывается до этапа 3. *Рекомендация: да.*
2. **Администрирование удалённо.** По умолчанию недоступно, включается для конкретного устройства на компьютере. *Рекомендация: да.*
3. **Ограниченный режим для удалённых задач.** Опция, по умолчанию выключена. *Рекомендация: оставить опцией.*
4. **Добавление первого устройства** только с компьютера (QR-код), без пароля на ретрансляторе. *Рекомендация: да. Пароль на сервере добавил бы ещё одну точку компрометации и не дал бы защиты от взлома самого сервера.*
5. **Размещение кода ретранслятора** в этом же репозитории (общий протокол и тесты, отдельный образ). *Рекомендация: да.*
6. **Несколько компьютеров** на одном ретрансляторе — этап 2. *Рекомендация: в MVP один.*
